## 2. รายละเอียดของโครงการ

จากการศึกษาและสำรวจกระบวนการประเมินทุนการศึกษาของคณะวิศวกรรมศาสตร์ มหาวิทยาลัยขอนแก่น พบว่าในปัจจุบันยังมีข้อจำกัดหลายประการ โดยเฉพาะในขั้นตอนการประเมินผู้สมัครทุน ซึ่งอาจารย์ผู้ประเมินจำเป็นต้องใช้งานหลายระบบและหลายไฟล์พร้อมกัน เช่น ระบบทุนการศึกษาของคณะ หน้าข้อมูลผู้สมัครเอกสารประกอบ โปรแกรมประชุมออนไลน์ และไฟล์ Excel สำหรับบันทึกคะแนน

การสลับไปมาระหว่างแหล่งข้อมูลเหล่านี้ในระหว่างการสัมภาษณ์หรือการพิจารณาทุน ทำให้กระบวนการประเมินขาดความต่อเนื่อง เพิ่มภาระในการตรวจสอบข้อมูลและเอกสาร และอาจส่งผลต่อความสะดวก ความรวดเร็ว และความถูกต้องในการให้คะแนน

นอกจากนี้ การบันทึกคะแนนและความคิดเห็นผ่านไฟล์แยกต่างหาก ทำให้ข้อมูลผู้สมัครและข้อมูลการประเมินไม่ได้ถูกจัดเก็บอยู่ในระบบเดียวกัน เมื่อมีการสร้างหรือแก้ไขไฟล์หลายชุด อาจทำให้เกิดปัญหาไฟล์หลายเวอร์ชัน คะแนนสูญหาย คะแนนถูกบันทึกผิดช่อง หรือมีการนำข้อมูลที่ไม่ใช่ฉบับล่าสุดมาใช้งาน

เมื่อการประเมินเสร็จสิ้น ผู้ดูแลระบบยังต้องรวบรวมผลการประเมินจากอาจารย์ผู้ประเมินแต่ละคนซึ่งเข้าร่วมประเมินผู้สมัครแต่ละราย คัดลอกข้อมูล และใช้สูตรในโปรแกรมตารางคำนวณเพื่อหาคะแนนรวมจากคะแนนรายเกณฑ์ รวมถึงจัดทำรายงานด้วยตนเอง กระบวนการดังกล่าวใช้เวลาค่อนข้างมากและมีความเสี่ยงต่อความผิดพลาดจากการคัดลอกข้อมูล การใช้สูตรคำนวณ และการจัดการไฟล์หลายเวอร์ชัน รวมถึงจัดทำรายงานด้วยตนเอง

ด้วยเหตุนี้ คณะผู้จัดทำจึงมีแนวคิดที่จะพัฒนาระบบบริหารจัดการการประเมินทุนการศึกษาในรูปแบบ Web Application เพื่อทำหน้าที่เป็นศูนย์กลางสำหรับอาจารย์ผู้ประเมินและผู้ดูแลระบบ โดยระบบจะรวบรวมข้อมูลผู้สมัคร เอกสารประกอบ ประวัติทุนย้อนหลัง เกณฑ์การให้คะแนน แบบฟอร์มประเมิน คะแนน ความคิดเห็น และผลสรุปการประเมินไว้ในระบบเดียวกัน

อาจารย์ผู้ประเมินจะสามารถดูข้อมูลผู้สมัครและบันทึกผลการประเมินผ่านระบบได้โดยตรง ส่วนผู้ดูแลระบบจะสามารถจัดการรอบทุน นำเข้าข้อมูลผู้สมัคร กำหนดเกณฑ์คะแนน ติดตามจำนวนและสถานะของผู้ประเมินในแต่ละราย ตรวจสอบผลการประเมิน และส่งออกรายงานได้อย่างเป็นระบบ อาจารย์ผู้ประเมินจะค้นหาและเลือกรายชื่อผู้สมัครที่กำลังสัมภาษณ์ผ่านระบบด้วยตนเอง โดยผู้สมัครหนึ่งคนสามารถได้รับการประเมินจากอาจารย์อย่างน้อย 2 คนและไม่เกิน 3 คนในแต่ละรอบทุน เมื่อมีผลการประเมินที่ยืนยันส่งสำเร็จแล้วจากอาจารย์ที่ไม่ซ้ำกันครบ 2 คน ระบบจะถือว่าผู้สมัครมีผลการประเมินครบขั้นต่ำ แต่ยังอนุญาตให้อาจารย์คนที่ 3 ส่งผลเพิ่มเติมได้ก่อนปิดรอบทุน ระบบจะป้องกันไม่ให้อาจารย์คนเดิมประเมินผู้สมัครรายเดิมซ้ำ และใช้เฉพาะผลที่ยืนยันส่งสำเร็จแล้วในการคำนวณผลสรุป

ระบบดังกล่าวมีเป้าหมายเพื่อลดการพึ่งพาไฟล์ Excel ลดความซ้ำซ้อนในการทำงาน ลดความผิดพลาดจากการจัดการข้อมูลด้วยตนเอง และเพิ่มประสิทธิภาพในการดำเนินกระบวนการประเมินทุนการศึกษาของคณะ

## 3. วัตถุประสงค์ของโครงการ

1. เพื่อพัฒนา Web Application สำหรับสนับสนุนกระบวนการประเมินทุนการศึกษาของคณะวิศวกรรมศาสตร์ มหาวิทยาลัยขอนแก่น ให้ครอบคลุมการใช้งานของอาจารย์ผู้ประเมินและผู้ดูแลระบบ

2. เพื่อรวบรวมข้อมูลผู้สมัคร เอกสารประกอบ ประวัติการสมัครหรือได้รับทุนย้อนหลัง และแบบฟอร์มการประเมินไว้ในระบบเดียวกัน

3. เพื่อให้อาจารย์ผู้ประเมินสามารถค้นหาและเลือกรายชื่อผู้สมัครที่กำลังสัมภาษณ์ เข้าถึงข้อมูลและเอกสารของผู้สมัครที่เลือก และบันทึกคะแนนกับความคิดเห็นได้อย่างสะดวกและต่อเนื่อง

4. เพื่อพัฒนาระบบจัดการเกณฑ์คะแนนที่รองรับการกำหนดหัวข้อการประเมินและคะแนนเต็มแยกตามรอบทุนรวมทั้งรองรับน้ำหนักคะแนนเมื่อได้รับการยืนยันเกี่ยวกับสูตรและวิธีใช้งาน

5. เพื่อพัฒนาระบบบันทึกแบบร่าง ตรวจสอบความถูกต้อง และยืนยันส่งผลการประเมินของอาจารย์ผู้ประเมิน

6. เพื่อพัฒนาระบบคำนวณผลสรุปของผู้สมัครจากคะแนนรายเกณฑ์ของอาจารย์ผู้ประเมินอย่างน้อย 2 คนและไม่เกิน 3 คน โดยใช้เฉพาะผลการประเมินที่ยืนยันส่งสำเร็จแล้ว และคำนวณผลตามสูตร น้ำหนักคะแนน และหลักการปัดเศษที่ได้รับการยืนยันจากงานทุน รวมถึงคำนวณผลสรุปใหม่เมื่ออาจารย์ผู้ประเมินคนที่ 3 ส่งผลเพิ่มเติม

7. เพื่อพัฒนาระบบจัดการรอบทุน และแยกข้อมูลผู้สมัคร เกณฑ์คะแนน การเลือกผู้สมัครของอาจารย์ผู้ประเมิน และผลการประเมินตามแต่ละรอบทุน รวมถึงควบคุมให้ผู้สมัครหนึ่งคนมีผู้ประเมินไม่เกิน 3 คน

8. เพื่อพัฒนาระบบติดตามสถานะการประเมิน เพื่อให้ผู้ดูแลระบบสามารถตรวจสอบจำนวนผู้ประเมินของผู้สมัครแต่ละราย จำนวนผลที่อยู่ในสถานะ Draft และ Submitted รวมถึงตรวจสอบว่าผู้สมัครยังไม่มีผลการประเมิน อยู่ระหว่างการประเมิน มีผล Submitted ครบขั้นต่ำ 2 คน หรือมีผล Submitted ครบสูงสุด 3 คนแล้ว

9. เพื่อพัฒนาระบบรายงานและส่งออกผลการประเมินในรูปแบบ Excel และ CSV สำหรับนำไปใช้ในกระบวนการของคณะ

10. เพื่อลดการพึ่งพาไฟล์ Excel ในการบันทึก รวบรวม และคำนวณคะแนน รวมถึงลดความผิดพลาดจากการจัดการข้อมูลด้วยตนเอง

11. เพื่อประเมินความสามารถในการใช้งานของระบบผ่านการทดสอบกับตัวแทนอาจารย์ผู้ประเมินและเจ้าหน้าที่งานทุน

### 3.1. เกณฑ์วัดความสำเร็จของโครงการ

การประเมินความสำเร็จของโครงการจะพิจารณาจากความถูกต้องของระบบ ความครบถ้วนของฟังก์ชันหลัก ความสามารถในการใช้งานจริง และผลตอบรับจากผู้ใช้งาน ดังนี้

| ตัวชี้วัด | เกณฑ์ความสำเร็จ |
|---|---|
| ความครบถ้วนของฟังก์ชันหลัก | ฟังก์ชัน Core ต้องได้รับการพัฒนาและผ่านการทดสอบตาม Test Case ที่กำหนด |
| ผลการทดสอบฟังก์ชัน | Test Case ของฟังก์ชัน Core ผ่านไม่น้อยกว่าร้อยละ 90 และไม่มีข้อผิดพลาดระดับ Critical ที่ขัดขวางกระบวนการหลัก |
| ความถูกต้องของการคำนวณคะแนน | คะแนนสรุปจากผล Submitted ของผู้ประเมินที่ไม่ซ้ำกัน 2-3 คนต้องตรงกับชุดข้อมูลตัวอย่างร้อยละ 100; ต้องคำนวณใหม่เมื่อผู้ประเมินคนที่ 3 Submit และต้องปฏิเสธผู้ประเมินคนที่ 4 รวมทั้งทดสอบ Draft และกรณี Submitted ไม่ครบ 2 คนตามกฎที่ยืนยัน |
| ความถูกต้องของการนำเข้าข้อมูล | ระบบต้องตรวจพบข้อมูลไม่ครบถ้วน ข้อมูลผิดรูปแบบ และข้อมูลซ้ำตามกรณีทดสอบที่กำหนด |
| ความถูกต้องของรายงาน | ข้อมูลในไฟล์ Excel และ CSV ต้องตรงกับข้อมูลสรุปผลในฐานข้อมูล |
| การควบคุมสิทธิ์ | ผู้ใช้ต้องไม่เข้าถึงเมนู API หรือข้อมูลนอกบทบาท; อาจารย์สร้าง แก้ไข และส่งได้เฉพาะผลประเมินของตนเอง |
| User Acceptance Testing | ตัวแทนอาจารย์ผู้ประเมินอย่างน้อย 2 คน และเจ้าหน้าที่งานทุนหรือผู้ดูแลระบบอย่างน้อย 2 คน ต้องทำกระบวนการหลักตามบทบาทสำเร็จโดยไม่มี Critical Defect |
| ความพึงพอใจของผู้ใช้งาน | คะแนนความพึงพอใจเฉลี่ยไม่น้อยกว่า 4.00 จาก 5.00 |
| ระยะเวลาคำนวณคะแนนรวมและสร้างรายงาน | ต้องลดลงจากวิธีเดิม โดยกำหนดเป้าหมายเชิงปริมาณหลังเก็บ Baseline ใน Phase 1 |
| ความพร้อมในการส่งมอบ | Source Code, Database Schema, Test Report และคู่มือการใช้งานต้องครบตามรายการส่งมอบ |

## 4. กลุ่มเป้าหมาย

### 4.1. อาจารย์ผู้ประเมิน

อาจารย์ที่เข้าร่วมกระบวนการสัมภาษณ์และประเมินผู้สมัครทุน โดยอาจารย์จะค้นหาและเลือกรายชื่อผู้สมัครที่กำลังสัมภาษณ์ผ่านระบบ จากนั้นสามารถดูข้อมูลและเอกสารของผู้สมัคร กรอกคะแนน บันทึกความคิดเห็น บันทึกแบบร่าง และยืนยันส่งผลการประเมินของตนเองผ่านระบบ

### 4.2. ผู้ดูแลระบบ

เจ้าหน้าที่หรือบุคลากรที่รับผิดชอบการจัดการกระบวนการประเมินทุน โดยสามารถจัดการผู้ใช้งาน รอบทุน ข้อมูลผู้สมัคร เอกสาร และเกณฑ์คะแนน รวมทั้งติดตามอาจารย์ที่เลือกประเมินผู้สมัครแต่ละราย ตรวจสอบจำนวนผู้ประเมินไม่ให้เกิน 3 คน ติดตามสถานะการประเมิน ตรวจสอบผลสรุป และส่งออกรายงาน

## 5. ขอบเขตการศึกษา

โครงการนี้มุ่งพัฒนา Web Application สำหรับบริหารจัดการกระบวนการประเมินทุนการศึกษา ตั้งแต่การเตรียมข้อมูลผู้สมัคร การจัดเก็บเอกสาร การกำหนดเกณฑ์ การค้นหาและเลือกผู้สมัครโดยอาจารย์ผู้ประเมินการให้คะแนนโดยผู้ประเมิน 2-3 คน การรวมผล และการส่งออกรายงาน

### 5.1. ขอบเขตด้านผู้ใช้งาน

#### 5.1.1. อาจารย์ผู้ประเมิน

1. เข้าสู่ระบบเพื่อใช้งานตามสิทธิ์ที่ได้รับ

2. ค้นหาและเลือกรายชื่อผู้สมัครที่กำลังสัมภาษณ์จากรอบทุนที่เปิดใช้งาน

3. ระบบต้องตรวจสอบว่าอาจารย์คนดังกล่าวไม่มีรายการประเมินที่ยังไม่ถูกยกเลิกสำหรับผู้สมัครรายนั้นและจำนวนรายการประเมินของผู้สมัครที่ยังไม่ถูกยกเลิกมีน้อยกว่า 3 รายการ ก่อนอนุญาตให้สร้างรายการประเมินใหม่

4. ดูข้อมูลพื้นฐานและข้อมูลประกอบการพิจารณาของผู้สมัคร

5. ดูเอกสารประกอบการพิจารณา

6. ดูประวัติการสมัครหรือได้รับทุนย้อนหลัง

7. ให้คะแนนตามเกณฑ์ของรอบทุน

8. บันทึกความคิดเห็นหรือข้อสังเกต

9. บันทึกผลการประเมินแบบร่าง

10. ตรวจสอบคะแนนและความคิดเห็นก่อนส่ง

11. ยืนยันส่งผลการประเมิน

#### 5.1.2. ผู้ดูแลระบบ

1. เข้าสู่ระบบเพื่อใช้งานตามสิทธิ์ที่ได้รับ

2. จัดการสิทธิ์ผู้ใช้งาน SEMS โดยเชื่อมโยงตัวตนจาก KKU Account กำหนดบทบาท ผู้ดูแลระบบ หรืออาจารย์ผู้ประเมิน และเปิดหรือปิดสิทธิ์การใช้งาน SEMS โดยไม่จัดการรหัสผ่าน KKU Account

3. จัดการรอบทุน

4. นำเข้าข้อมูลผู้สมัครจากไฟล์ CSV หรือ Excel

5. ตรวจสอบข้อมูลก่อนยืนยันการนำเข้า

6. จัดการข้อมูลและเอกสารประกอบของผู้สมัคร

7. จัดการเกณฑ์คะแนนของแต่ละรอบทุน

8. ติดตามรายชื่ออาจารย์ผู้ประเมินที่เลือกประเมินผู้สมัครแต่ละราย โดยผู้สมัครหนึ่งคนต้องมีผลการประเมินครบขั้นต่ำจากอาจารย์อย่างน้อย 2 คน และสามารถมีผู้ประเมินได้สูงสุดไม่เกิน 3 คน ส่วนผู้ประเมินหนึ่งคนสามารถประเมินผู้สมัครได้หลายคน

9. ติดตามสถานะการประเมิน

10. ดูรายชื่อผู้ประเมินของผู้สมัครแต่ละราย คะแนนรายเกณฑ์และคะแนนรวมของผู้ประเมินแต่ละคนจำนวนผลที่ Submitted สถานะ ความคิดเห็น และผลสรุปของผู้สมัครตามสูตรที่ได้รับการยืนยัน

11. ส่งออกรายงานในรูปแบบ Excel และ CSV

12. ตรวจสอบประวัติการดำเนินการตามขอบเขตที่กำหนด

### 5.2. ขอบเขตด้านฟังก์ชันการทำงาน

#### 5.2.1. ระบบเข้าสู่ระบบและควบคุมสิทธิ์

1. ระบบรองรับการเข้าสู่ระบบด้วยบัญชี KKU Account ผ่านระบบ Single Sign-On ของมหาวิทยาลัย

2. ระบบต้องส่งผู้ใช้งานไปยังระบบ KKU SSO เพื่อดำเนินการยืนยันตัวตน และต้องไม่รับหรือจัดเก็บรหัสผ่าน KKU Account ภายในระบบ SEMS

3. ระบบต้องตรวจสอบผลการยืนยันตัวตนที่ได้รับจาก KKU SSO ก่อนสร้าง Session สำหรับการใช้งาน

4. หลังยืนยันตัวตนสำเร็จ ระบบต้องตรวจสอบว่าผู้ใช้ได้รับอนุญาตให้ใช้งาน SEMS และบัญชี SEMS อยู่ในสถานะ Active

5. ระบบรองรับบทบาทผู้ใช้งานอย่างน้อย 2 บทบาท ได้แก่ ผู้ดูแลระบบ และ อาจารย์ผู้ประเมิน

6. ระบบต้องจำกัดเมนู ฟังก์ชัน API และข้อมูลตามบทบาท

7. ระบบต้องอนุญาตให้ อาจารย์ผู้ประเมิน ค้นหาและดูข้อมูลที่จำเป็นสำหรับเลือกรายชื่อผู้สมัครในรอบทุนที่เปิดใช้งานได้ เมื่อผู้ประเมินเลือกผู้สมัครแล้ว ระบบต้องสร้างสิทธิ์สำหรับการประเมินรายการนั้น และจำกัดให้ผู้ประเมินเข้าถึง แก้ไข หรือส่งได้เฉพาะผลการประเมินของตนเอง

8. ผู้ดูแลระบบสามารถเพิ่มหรือเชื่อมโยงผู้ใช้ KKU Account เข้ากับบัญชี SEMS กำหนดบทบาท และเปิดหรือปิดสิทธิ์การใช้งาน SEMS

9. ระบบต้องรองรับการออกจากระบบ SEMS และยกเลิก Session ของระบบตามแนวทางที่ได้รับการยืนยัน

10. รายละเอียด Protocol, Client Registration, Redirect URI, Claims และ Logout Flow ต้องเป็นไปตามข้อกำหนดของหน่วยงานผู้ดูแล KKU SSO

#### 5.2.2. ระบบจัดการรอบทุน

1. สร้างและแก้ไขข้อมูลรอบทุน

2. กำหนดสถานะของรอบทุน เช่น Draft, Open, Closed และ Archived

3. แยกข้อมูลผู้สมัคร เกณฑ์คะแนน รายการเลือกผู้สมัครของอาจารย์ และผลการประเมินตามรอบทุน

4. จำกัดการแก้ไขหรือลบรอบทุนที่มีผลประเมินแล้ว

#### 5.2.3. ระบบนำเข้าข้อมูลผู้สมัคร

1. รองรับไฟล์ CSV และ Excel ที่จัดเตรียมโดยงานทุนของคณะ

2. อ่านข้อมูลผู้สมัครจากไฟล์และแสดงตัวอย่างก่อนนำเข้า

3. รองรับการจับคู่คอลัมน์จากไฟล์กับฟิลด์ในระบบ

4. ตรวจสอบข้อมูลที่จำเป็นต่อการประเมิน

5. ตรวจสอบข้อมูลไม่ครบถ้วน ข้อมูลผิดรูปแบบ และข้อมูลซ้ำ

6. แสดงเลขแถวและรายละเอียดของข้อมูลที่มีปัญหา

7. ยืนยันการนำเข้าข้อมูลเข้าสู่รอบทุนที่เลือก

8. จัดเก็บประวัติการนำเข้า เช่น ชื่อไฟล์ วันที่นำเข้า ผู้นำเข้า และจำนวนรายการ

#### 5.2.4. ระบบจัดการข้อมูลผู้สมัคร

1. แสดงข้อมูลพื้นฐานของผู้สมัคร

2. แสดงข้อมูลประกอบการพิจารณาที่นำเข้าจากระบบเดิม

3. แสดงประวัติการสมัครหรือได้รับทุนย้อนหลัง

4. แสดงรายการเอกสารประกอบ

5. รองรับการค้นหาและกรองข้อมูลผู้สมัคร

6. แยกข้อมูลผู้สมัครตามรอบทุน

#### 5.2.5. ระบบจัดการเอกสารประกอบ

1. เอกสารประกอบการพิจารณา เช่น PDF, JPG หรือ PNG จะถูกอัปโหลดเข้าสู่ระบบโดยผู้ดูแลระบบหลังจากนำเข้าข้อมูลผู้สมัครแล้ว โดยผู้ดูแลระบบจะเลือกผู้สมัครและแนบเอกสารที่เกี่ยวข้องกับผู้สมัครแต่ละราย

2. ไฟล์เอกสารจะถูกจัดเก็บใน File Storage ของ Server หรือ Object Storage ที่ระบบกำหนด ส่วนฐานข้อมูล PostgreSQL จะจัดเก็บเฉพาะข้อมูลอ้างอิงของไฟล์ เช่น ชื่อไฟล์ ประเภทไฟล์ ขนาดไฟล์ ตำแหน่งจัดเก็บ ผู้ที่อัปโหลด และวันที่อัปโหลด

3. ระบบจะรองรับการเปิดดูไฟล์ PDF, JPG และ PNG ผ่าน Browser ตามความสามารถของระบบ ส่วนไฟล์ที่ไม่สามารถเปิดดูได้โดยตรงจะรองรับการดาวน์โหลด โดยการเข้าถึงเอกสารต้องผ่านการตรวจสอบสิทธิ์ทุกครั้ง

#### 5.2.6. ระบบจัดการประวัติทุนย้อนหลัง

1. ประวัติการสมัครหรือได้รับทุนย้อนหลังจะนำเข้าจากไฟล์ CSV หรือ Excel ที่งานทุนของคณะจัดเตรียมโดยใช้รหัสนักศึกษาเป็นข้อมูลสำหรับเชื่อมโยงกับผู้สมัครในรอบทุนปัจจุบัน

2. หากข้อมูลประวัติทุนไม่ได้อยู่ในไฟล์ข้อมูลผู้สมัครหลัก ระบบจะรองรับการนำเข้าจากไฟล์ประวัติทุนแยกต่างหากโดยผู้ดูแลระบบ ระบบจะไม่เชื่อมต่อกับฐานข้อมูลของระบบทุนเดิมโดยตรงในขอบเขตของโครงการนี้

#### 5.2.7. ระบบจัดการเกณฑ์คะแนน

1. สร้างและแก้ไขชุดเกณฑ์คะแนนของแต่ละรอบทุน

2. กำหนดหัวข้อการประเมิน คำอธิบาย และคะแนนเต็ม โดยรองรับน้ำหนักคะแนนเมื่อได้รับการยืนยันเกี่ยวกับสูตร รูปแบบน้ำหนัก และวิธีคำนวณ

3. ตรวจสอบความครบถ้วนของเกณฑ์ก่อนเปิดใช้งาน

4. จัดเก็บเกณฑ์แยกตามรอบทุน

5. จำกัดการแก้ไขเกณฑ์ที่เริ่มมีการประเมินแล้ว

6. รองรับการสร้างเวอร์ชันใหม่ของเกณฑ์เมื่อมีการเปลี่ยนแปลงที่กระทบคะแนน

#### 5.2.8. ระบบเลือกผู้สมัครและควบคุมจำนวนผู้ประเมิน

1. ระบบแสดงรายการผู้สมัครในรอบทุนที่เปิดใช้งาน และรองรับการค้นหาด้วยรหัสนักศึกษา ชื่อ หรือนามสกุล

2. อาจารย์ผู้ประเมินสามารถเลือกรายชื่อผู้สมัครที่กำลังสัมภาษณ์เพื่อเริ่มการประเมินได้ด้วยตนเอง

3. ผู้สมัครหนึ่งคนต้องมีผลการประเมินที่ Submitted จากอาจารย์ผู้ประเมินที่ไม่ซ้ำกันอย่างน้อย 2 คน จึงจะถือว่าผลการประเมินครบขั้นต่ำ และสามารถมีอาจารย์ผู้ประเมินได้สูงสุดไม่เกิน 3 คนในแต่ละรอบทุนเมื่อผู้สมัครมีผล Submitted ครบ 2 คนแล้ว ระบบยังต้องอนุญาตให้อาจารย์ผู้ประเมินคนที่ 3 เลือกและประเมินผู้สมัครรายดังกล่าวได้ ตราบใดที่รอบทุนยังอยู่ในสถานะ Open และจำนวนรายการประเมินที่ยังไม่ถูกยกเลิกมีน้อยกว่า 3 รายการ

4. ผู้ประเมินหนึ่งคนสามารถประเมินผู้สมัครได้หลายคน แต่ไม่สามารถประเมินผู้สมัครคนเดิมซ้ำในรอบทุนเดียวกัน

5. ก่อนสร้างรายการประเมิน ระบบต้องตรวจสอบว่าบัญชีผู้ประเมินอยู่ในสถานะ Active รอบทุนอยู่ในสถานะ Open ผู้ประเมินไม่มีรายการประเมินที่ยังไม่ถูกยกเลิกสำหรับผู้สมัครรายนั้น และจำนวนรายการประเมินของผู้สมัครที่ยังไม่ถูกยกเลิกมีน้อยกว่า 3 รายการ

6. ระบบต้องป้องกันกรณีอาจารย์หลายคนเลือกผู้สมัครรายเดียวกันพร้อมกันแล้วทำให้จำนวนผู้ประเมินเกิน 3 คน โดยใช้ Database Transaction หรือกลไกควบคุมที่เหมาะสม

7. การยกเลิกการเลือกผู้สมัครก่อน Submit ต้องได้รับอนุญาตตามสิทธิ์และบันทึกประวัติการดำเนินการ

8. การแก้ไขหรือยกเลิกผลหลัง Submit ต้องเป็นไปตาม Reopen Policy ที่ได้รับการยืนยัน

9. ระบบ SEMS ไม่รับผิดชอบการจัดลำดับคิว การจัดห้องสัมภาษณ์ หรือการดึงอาจารย์และผู้สมัครเข้าสู่ห้องประชุมออนไลน์

10. เมื่อรอบทุนเปลี่ยนเป็นสถานะ Closed ระบบต้องไม่อนุญาตให้อาจารย์สร้างรายการประเมินใหม่หรือส่งผลการประเมินเพิ่มเติม เว้นแต่ผู้ดูแลระบบจะเปิดรอบทุนหรือดำเนินการตามกระบวนการอนุมัติที่กำหนด

#### 5.2.9. ระบบประเมินทุน

1. แสดงข้อมูลผู้สมัคร ข้อมูลประกอบที่อยู่ในขอบเขต เกณฑ์ และแบบฟอร์มประเมินในหน้าเดียว

2. จำกัดให้อาจารย์ผู้ประเมินกรอก แก้ไข และส่งผลได้เฉพาะผู้สมัครที่ตนเลือกและระบบได้สร้างรายการประเมินไว้แล้ว โดยอาจารย์คนเดิมต้องไม่สามารถมีรายการประเมินที่ยังไม่ถูกยกเลิกมากกว่าหนึ่งรายการสำหรับผู้สมัครรายเดิมในรอบทุนเดียวกัน

3. ก่อนสร้างรายการประเมินใหม่ ระบบต้องตรวจสอบจำนวนรายการประเมินที่ยังไม่ถูกยกเลิกของผู้สมัครอีกครั้ง เพื่อป้องกันไม่ให้จำนวนผู้ประเมินเกิน 3 คน ทั้งนี้ ผู้ประเมินที่มีรายการประเมินอยู่แล้วต้องสามารถกลับมาแก้ไข Draft ของตนได้ตามสิทธิ์

4. แสดงเกณฑ์ตามรอบทุนที่ผู้สมัครสังกัด

5. รองรับการกรอกคะแนนแยกตามหัวข้อ

6. ตรวจสอบคะแนนไม่ให้ต่ำกว่าค่าต่ำสุดหรือสูงกว่าคะแนนเต็ม

7. ตรวจสอบความครบถ้วนของข้อมูลก่อน Submit ตามกฎที่ได้รับการยืนยัน

8. รองรับการบันทึกความคิดเห็น

9. รองรับการบันทึกผลการประเมินแบบร่างด้วยตนเอง

10. แสดงหน้าตรวจสอบคะแนนและความคิดเห็นก่อนยืนยัน

11. รองรับการยืนยันส่งผลการประเมิน

12. เมื่อ Submit สำเร็จ ระบบต้องเปลี่ยนสถานะเป็น Submitted

13. ป้องกันการนำคะแนนแบบร่างไปใช้เป็นผลคะแนนสุดท้าย

14. การแก้ไขหรือเปิดผลหลัง Submit ต้องเป็นไปตาม Reopen Policy ที่ได้รับการยืนยัน

#### 5.2.10. ระบบคำนวณคะแนนและสรุปผลการประเมิน

1. ระบบต้องดึงผลการประเมินของผู้สมัครจากอาจารย์ผู้ประเมินที่ไม่ซ้ำกันจำนวนไม่เกิน 3 คนในรอบทุนนั้น

2. ผลการประเมินหนึ่งรายการต้องเชื่อมโยงกับผู้สมัคร รอบทุน และอาจารย์ผู้ประเมินอย่างชัดเจน

3. อาจารย์หนึ่งคนต้องมีผลการประเมินสำหรับผู้สมัครหนึ่งคนได้ไม่เกินหนึ่งรายการในรอบทุนเดียวกัน

4. ระบบต้องใช้เฉพาะผลการประเมินที่มีสถานะ Submitted ในการคำนวณผลสรุป

5. ผลที่มีสถานะ Draft หรือผลที่ยังไม่ได้ Submit ต้องไม่ถูกนำไปใช้ในการคำนวณคะแนนสรุป

6. ระบบต้องแสดงจำนวนผล Submitted ในรูปแบบ 0/3, 1/3, 2/3 หรือ 3/3 และกำหนดสถานะของผู้สมัครดังนี้

- Not Started: ยังไม่มีรายการประเมินที่ใช้งานอยู่

- In Progress: มีรายการประเมินที่ยังไม่ถูกยกเลิกอย่างน้อยหนึ่งรายการ และมีผล Submitted น้อยกว่า 2 รายการ

- Minimum Complete: มีผล Submitted จากผู้ประเมินที่ไม่ซ้ำกันครบ 2 รายการ และรอบทุนยังเปิดอยู่

- Fully Complete: มีผล Submitted จากผู้ประเมินที่ไม่ซ้ำกันครบ 3 รายการ และรอบทุนยังเปิดอยู่

- Finalized: รอบทุนถูกปิดและผู้สมัครมีผล Submitted อย่างน้อย 2 รายการ โดยระบบยืนยันผลสรุปล่าสุดเป็นผลสุดท้าย

- Closed Incomplete: รอบทุนถูกปิดแต่ผู้สมัครมีผล Submitted น้อยกว่า 2 รายการ จึงยังไม่มีคะแนนสรุปสุดท้าย

7. ระบบต้องคำนวณคะแนนของผู้ประเมินแต่ละคนจากคะแนนรายเกณฑ์ตามกฎที่ได้รับการยืนยัน

8. เมื่อมีผล Submitted จากผู้ประเมินที่ไม่ซ้ำกันครบอย่างน้อย 2 คน ระบบต้องคำนวณคะแนนสรุปของผู้สมัครตามสูตร น้ำหนัก และหลักการปัดเศษที่ได้รับการยืนยัน โดยผลสรุปที่คำนวณจากผู้ประเมิน 2 คนสามารถเปลี่ยนแปลงได้หากมีผู้ประเมินคนที่ 3 Submit เพิ่มเติมก่อนปิดรอบทุน

9. เมื่อผู้ประเมินคนที่ 3 Submit ผลเพิ่มเติม ระบบต้องนำผล Submitted ของผู้ประเมินทั้ง 3 คนมาคำนวณผลสรุปใหม่โดยอัตโนมัติ และปรับปรุงข้อมูลใน Result Summary, Dashboard และรายงานให้สอดคล้องกัน

10. ระบบต้องแสดงรายชื่อผู้ประเมิน คะแนนรายเกณฑ์ คะแนนรวมรายผู้ประเมิน จำนวนผล Submitted สถานะ ความคิดเห็น และคะแนนสรุปของผู้สมัคร

11. ระบบต้องรองรับการค้นหา กรอง และจัดเรียงผลตามรอบทุน จำนวนผู้ประเมิน สถานะ หรือคะแนนสรุป

12. ผู้สมัครหนึ่งคนต้องมี Result Summary ได้ไม่เกินหนึ่งรายการต่อรอบทุน และสามารถมี Evaluation ที่ยังไม่ถูกยกเลิกได้ไม่เกิน 3 รายการ โดยระบบจะคำนวณ Result Summary เมื่อมีผล Submitted จากผู้ประเมินที่ไม่ซ้ำกันครบอย่างน้อย 2 รายการ

13. ผลสรุปที่คำนวณเมื่อมีผู้ประเมินครบขั้นต่ำ 2 คนถือเป็นผลสรุปล่าสุดของระบบ แต่ยังสามารถเปลี่ยนแปลงได้หากมีผู้ประเมินคนที่ 3 Submit ก่อนปิดรอบทุน เมื่อรอบทุนถูกปิด ระบบจึงถือผลสรุปล่าสุดเป็นผลสรุปสุดท้ายของรอบทุนนั้น

#### 5.2.11. ระบบรายงาน

1. แสดงผลสรุปการประเมินของผู้สมัคร

2. ส่งออกรายงานในรูปแบบ Excel และ CSV ตามรูปแบบที่กำหนด

3. รายงานต้องประกอบด้วยข้อมูลผู้สมัคร รายชื่อผู้ประเมินที่ส่งผล คะแนนรายเกณฑ์และคะแนนรวมของผู้ประเมินแต่ละคน จำนวนผู้ประเมิน จำนวนผล Submitted สถานะ ความคิดเห็น และคะแนนสรุปของผู้สมัครตามสิทธิ์

4. คะแนนสรุปในรายงานต้องคำนวณจากผลการประเมินที่มีสถานะ Submitted ของผู้ประเมินที่ไม่ซ้ำกันเท่านั้น โดยผล Draft หรือผลที่ถูกยกเลิกต้องไม่ถูกนำไปคำนวณ

5. ข้อมูลในรายงานต้องตรงกับข้อมูล Result Summary และข้อมูลในฐานข้อมูล

6. บันทึกข้อมูลผู้ที่ส่งออกรายงานและเวลาที่ดำเนินการ

7. การส่งออก PDF และ Custom Report Template เป็นฟังก์ชันเสริม

8. รายงานต้องแสดงจำนวนผล Submitted ของผู้สมัคร และระบุสถานะว่าเป็น Minimum Complete เมื่อมีผล Submitted จำนวน 2 คน หรือ Fully Complete เมื่อมีผล Submitted จำนวน 3 คน หากรอบทุนยังไม่ปิด คะแนนสรุปที่มีผู้ประเมิน 2 คนต้องถือเป็นผลสรุปล่าสุดซึ่งอาจเปลี่ยนแปลงได้เมื่อมีผลจากผู้ประเมินคนที่ 3

9. เมื่อรอบทุนถูกปิด รายงานต้องแสดงสถานะ Finalized สำหรับผู้สมัครที่มีผล Submitted อย่างน้อย 2 รายการ และแสดงสถานะ Closed Incomplete สำหรับผู้สมัครที่มีผล Submitted น้อยกว่า 2 รายการ โดยผู้สมัครที่มีสถานะ Closed Incomplete ต้องไม่มีคะแนนสรุปสุดท้าย

### 5.5. แนวทางการคุ้มครองข้อมูลส่วนบุคคล

ข้อมูลผู้สมัครทุนอาจประกอบด้วยข้อมูลส่วนบุคคลและข้อมูลที่ต้องได้รับการคุ้มครองเป็นพิเศษ เช่น ข้อมูลติดต่อข้อมูลผลการศึกษา ข้อมูลรายได้ และข้อมูลฐานะครอบครัว ระบบจึงกำหนดแนวทางการจัดการข้อมูลดังนี้

1. ผู้ใช้งานต้องเข้าสู่ระบบก่อนเข้าถึงข้อมูล

2. ระบบต้องจำกัดสิทธิ์ตามบทบาท รอบทุนที่เปิดใช้งาน และรายการประเมินที่ผู้ประเมินเป็นเจ้าของ

3. อาจารย์ผู้ประเมินสามารถค้นหารายชื่อผู้สมัครในรอบทุนที่เปิดใช้งานได้ โดยระบบควรแสดงข้อมูลเท่าที่จำเป็นสำหรับการค้นหาและเลือกผู้สมัคร ส่วนข้อมูลรายละเอียด เอกสาร และข้อมูลส่วนบุคคลที่ละเอียดอ่อนจะแสดงเมื่ออาจารย์เริ่มการประเมินผู้สมัครรายนั้นแล้ว

4. ผู้ดูแลระบบสามารถเข้าถึงข้อมูลตามหน้าที่ที่รับผิดชอบ

5. การเข้าถึงเอกสารต้องผ่าน Backend และการตรวจสอบสิทธิ์

6. การรับส่งข้อมูลในสภาพแวดล้อมใช้งานจริงต้องใช้ HTTPS

7. ระบบ SEMS ต้องไม่รับหรือจัดเก็บรหัสผ่าน KKU Account การยืนยันรหัสผ่านให้ดำเนินการโดยระบบ KKU SSO ส่วน SEMS ต้องจัดเก็บเฉพาะข้อมูลระบุตัวตนที่จำเป็น ข้อมูลบทบาท สถานะการอนุญาตและข้อมูล Session ตามขอบเขตที่ได้รับอนุมัติ

8. ระบบต้องไม่จัดเก็บรหัสผ่าน Token หรือข้อมูลลับไว้ใน Audit Log

9. ในระหว่างการพัฒนาและทดสอบ จะใช้ข้อมูลจำลองหรือข้อมูลที่ผ่านการปกปิดตัวตน

10. หากจำเป็นต้องใช้ข้อมูลจริง ต้องได้รับอนุญาตจากหน่วยงานเจ้าของข้อมูลก่อน

11. ห้ามนำข้อมูลจริงไปจัดเก็บใน Source Code หรือ Public Repository

12. ไฟล์ Configuration และ Environment Variable ต้องแยกออกจาก Source Code

13. ต้องกำหนดระยะเวลาการจัดเก็บและการลบข้อมูลตามนโยบายของคณะหรือมหาวิทยาลัยก่อนนำระบบไปใช้งานจริง

## 7. ความรู้พื้นฐาน

### 7.1. Web Application Development

ความรู้เกี่ยวกับการพัฒนาระบบเว็บแบบ Client-Server การทำงานของ Browser, Web Server และ Database รวมถึงการรับส่งข้อมูลผ่าน HTTP หรือ HTTPS

### 7.2. Frontend Development

ความรู้เกี่ยวกับการพัฒนาส่วนติดต่อผู้ใช้งานด้วย Next.js และ TypeScript การแบ่ง Component การจัดการ State การตรวจสอบข้อมูลใน Form การจัดการ Routing และการออกแบบหน้าจอตามบทบาทของผู้ใช้งาน

### 7.3. Backend Development

ความรู้เกี่ยวกับการพัฒนา Backend ด้วย NestJS การแบ่ง Module, Controller, Service และ Data Access Layer รวมถึงการเขียน Business Logic และการจัดการข้อผิดพลาด

### 7.4. API Development

ความรู้เกี่ยวกับการออกแบบ REST API การกำหนด Endpoint, HTTP Method, Request, Response, Status Code และรูปแบบ Error Message ที่สอดคล้องกัน

### 7.5. Database Design

ความรู้เกี่ยวกับการออกแบบฐานข้อมูลเชิงสัมพันธ์ การกำหนด Entity, Primary Key, Foreign Key, Constraint, Index และ Transaction รวมถึงการออกแบบข้อมูลให้รองรับรอบทุน ผู้สมัคร เกณฑ์ รายการเลือกผู้สมัครของผู้ประเมิน ผลการประเมินรายบุคคล และผลสรุปจากผู้ประเมินหลายคน โดยต้องกำหนด Constraint ป้องกันผู้ประเมินคนเดิมประเมินผู้สมัครซ้ำในรอบทุนเดียวกัน

### 7.6. Object-Relational Mapping

ความรู้เกี่ยวกับการใช้ Prisma สำหรับเชื่อมต่อ Backend กับ PostgreSQL การกำหนด Schema การ Query ข้อมูล และการจัดการ Database Migration

### 7.7. Authentication และ Authorization

ความรู้เกี่ยวกับการเชื่อมต่อระบบ Single Sign-On การ Redirect ผู้ใช้ไปยัง Identity Provider การรับและตรวจสอบผลการยืนยันตัวตน การจัดการ Callback การสร้างและยกเลิก Session การป้องกันการปลอมแปลง Request และการควบคุมสิทธิ์ด้วย Role-Based Access Control ระบบ KKU SSO ใช้สำหรับ Authentication ส่วนระบบ SEMS ยังคงรับผิดชอบ Authorization ได้แก่ การกำหนดบทบาท ผู้ดูแลระบบและ อาจารย์ผู้ประเมิน การเปิดหรือปิดสิทธิ์ใช้งาน และการจำกัดข้อมูลตามบทบาท รอบทุน และความเป็นเจ้าของรายการประเมิน รวมถึงการตรวจสอบสิทธิ์ก่อนเลือกผู้สมัคร เปิดดูเอกสาร บันทึก Draft และ Submit ผลการประเมิน

### 7.8. File Upload และ File Storage

ความรู้เกี่ยวกับการอัปโหลดไฟล์ การตรวจสอบชนิดและขนาดไฟล์ การจัดเก็บไฟล์นอกฐานข้อมูล การสร้าง URL หรือ Path อ้างอิง และการตรวจสอบสิทธิ์ก่อนดาวน์โหลดหรือเปิดดูเอกสาร

### 7.9. Data Import และ Validation

ความรู้เกี่ยวกับการอ่านไฟล์ CSV และ Excel การจับคู่คอลัมน์ การตรวจสอบข้อมูลบังคับ ข้อมูลผิดรูปแบบ และข้อมูลซ้ำ รวมถึงการใช้ Transaction ในการนำเข้าข้อมูล

### 7.10. Scoring และ Business Logic

ความรู้เกี่ยวกับการตรวจสอบคะแนนรายเกณฑ์ การคำนวณคะแนนรวมรายผู้ประเมิน และการคำนวณคะแนนสรุปจากผลการประเมินของผู้ประเมิน 2-3 คน โดยใช้เฉพาะผลที่มีสถานะ Submitted รวมถึงการรองรับน้ำหนักคะแนน สูตรคำนวณ และหลักการปัดเศษที่ได้รับการยืนยัน

### 7.11. Security และการคุ้มครองข้อมูลส่วนบุคคล

ความรู้เกี่ยวกับการควบคุมสิทธิ์ การป้องกันข้อมูลรั่วไหล การใช้ HTTPS การจัดการข้อมูลส่วนบุคคล การปกปิดตัวตนของข้อมูลทดสอบ และแนวทางป้องกันความเสี่ยงพื้นฐานของ Web Application

### 7.12. Software Testing

ความรู้เกี่ยวกับ Unit Testing, Integration Testing, End-to-End Testing, Security Testing, Regression Testing และ User Acceptance Testing

### 7.13. Version Control

ความรู้เกี่ยวกับการใช้ Git และ GitHub การจัดการ Branch, Commit, Pull Request และการแก้ไข Conflict ในการทำงานร่วมกัน

### 7.14. Deployment และ System Operation

ความรู้เกี่ยวกับการกำหนด Environment Variable การติดตั้ง Frontend, Backend, Database และ File Storage การสำรองข้อมูล การใช้ Domain และ HTTPS Certificate รวมถึงการแยก Development, Testing และ Production Environment

### 7.15. สถาปัตยกรรมระบบเบื้องต้น

ระบบใช้สถาปัตยกรรมแบบ Client-Server โดยผู้ใช้งานเข้าถึงระบบผ่าน Web Browser และติดต่อกับ Frontend ซึ่งพัฒนาด้วย Next.js จากนั้น Frontend จะเรียกใช้งาน REST API ของ Backend ซึ่งพัฒนาด้วย NestJS

Backend ทำหน้าที่ตรวจสอบตัวตนและสิทธิ์ ประมวลผล Business Logic ติดต่อฐานข้อมูล PostgreSQL และจัดการ File Storage สำหรับเอกสารประกอบ

องค์ประกอบหลักของระบบประกอบด้วย

1. Next.js Frontend สำหรับแสดงผลและรับข้อมูลจากผู้ใช้งาน

2. NestJS Backend สำหรับประมวลผลกฎทางธุรกิจ ตรวจสอบสิทธิ์ และจัดการ API

3. PostgreSQL Database สำหรับจัดเก็บข้อมูลเชิงโครงสร้าง

4. File Storage สำหรับจัดเก็บเอกสารประกอบ

5. Authentication และ RBAC สำหรับควบคุมการเข้าถึงระบบ

6. HTTPS สำหรับป้องกันข้อมูลระหว่างการรับส่งในสภาพแวดล้อมใช้งานจริง

### 7.16. แผนการติดตั้งระบบ

ระบบมีแผนติดตั้งบน Server ที่คณะหรือมหาวิทยาลัยจัดเตรียม โดยคณะผู้จัดทำจะประสานงานเกี่ยวกับทรัพยากร Server, Domain, HTTPS Certificate, Database, File Storage และสิทธิ์การเข้าถึงตั้งแต่ Phase 1

หาก Server ของคณะไม่พร้อมภายในระยะเวลาที่กำหนด จะใช้ Cloud Server สำหรับการพัฒนา การทดสอบและการสาธิตระบบ จากนั้นจึงย้ายระบบไปยังสภาพแวดล้อมของคณะเมื่อได้รับอนุญาตและมีทรัพยากรพร้อม

แนวทางการติดตั้งประกอบด้วย

1. แยก Development, Testing และ Production Environment ตามทรัพยากรที่มี

2. แยก Environment Variable และข้อมูลลับออกจาก Source Code

3. จำกัดการเข้าถึง PostgreSQL จากภายนอก

4. ใช้ HTTPS ในสภาพแวดล้อมใช้งานจริง

5. กำหนด Directory หรือ Object Storage สำหรับเอกสาร

6. จัดทำ Database Migration

7. จัดทำบัญชีผู้ดูแลระบบเริ่มต้น

8. จัดทำแผนสำรองและกู้คืนฐานข้อมูล

9. ตรวจสอบ Permission ของ File Storage

10. จัดทำคู่มือการติดตั้งและตั้งค่าระบบ

4. ลดความผิดพลาดจากการคัดลอกข้อมูลและการใช้ไฟล์หลายเวอร์ชัน

5. ผู้ดูแลระบบสามารถจัดการรอบทุน ผู้สมัคร เอกสาร และเกณฑ์คะแนน รวมถึงติดตามรายชื่อผู้ประเมินและสถานะการประเมินของผู้สมัครแต่ละรายได้อย่างเป็นระบบ

6. ระบบสามารถตรวจสอบความถูกต้องของคะแนนก่อนส่งผล

7. ระบบสามารถคำนวณคะแนนรวมรายผู้ประเมินและคะแนนสรุปของผู้สมัครได้โดยอัตโนมัติเมื่อมีผล Submitted ครบขั้นต่ำ 2 คน และสามารถคำนวณผลสรุปใหม่เมื่อมีผล Submitted จากผู้ประเมินคนที่ 3 ก่อนปิดรอบทุน

8. ผู้ดูแลระบบสามารถติดตามสถานะการประเมินได้อย่างชัดเจน

9. สามารถส่งออกรายงาน Excel และ CSV ที่พร้อมนำไปใช้งานต่อ

10. เพิ่มความถูกต้อง ความรวดเร็ว และความสามารถในการตรวจสอบย้อนหลัง

11. ลดเวลาที่ใช้ในการรวบรวมและคำนวณคะแนนจากคะแนนรายเกณฑ์ รวมถึงการจัดทำรายงาน

12. เป็นพื้นฐานสำหรับการขยายระบบหรือเชื่อมต่อระบบอื่นในอนาคต
