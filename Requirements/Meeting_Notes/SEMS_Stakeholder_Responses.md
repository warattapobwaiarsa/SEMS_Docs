# 1. ข้อมูลส่วนบุคคลและ Repository

### Q-001 ข้อมูลตัวอย่างใน Repository เป็นข้อมูลจำลองทั้งหมดหรือไม่?

**คำตอบจาก Stakeholder:** ยืนยันให้ใช้เฉพาะข้อมูลจำลองหรือข้อมูลที่ผ่านการปกปิดตัวตนแล้วใน Repository และสภาพแวดล้อม Development/Test ห้ามนำข้อมูลนักศึกษาจริง เอกสารจริง Token Secret หรือไฟล์ Export จริงขึ้น Public Repository

หากภายหลังพบข้อมูลจริง ให้ดำเนินการทันทีดังนี้: ลบไฟล์ ปกปิดข้อมูล ตรวจ Git history เปลี่ยน Secret ที่อาจรั่ว และรายงานอาจารย์ที่ปรึกษากับเจ้าของข้อมูล

### Q-002 อนุญาตให้เผยแพร่ชื่อและรหัสนักศึกษาของผู้จัดทำใน Public Repository หรือไม่?

**คำตอบจาก Stakeholder:** อนุญาตให้แสดงชื่อผู้จัดทำและรหัสนักศึกษาใน Proposal หรือเอกสารระบุตัวโครงการได้ แต่ไม่ควรนำรหัสไปใส่ซ้ำในไฟล์ตัวอย่าง ฐานข้อมูลทดสอบ หรือหน้าจอ Wireframe โดยไม่จำเป็น

### Q-003 ควรเปลี่ยน Repository เป็น Private ชั่วคราวหรือไม่?

**คำตอบจาก Stakeholder:** เมื่อยืนยันแล้วว่าข้อมูลทั้งหมดเป็นข้อมูลจำลองและไม่มี Secret สามารถคง Repository เป็น Public ได้ แต่ก่อน Commit ทุกครั้งต้องมีการตรวจ PII/Secret และ `.env`, Key, Token, Production Export ต้องถูกป้องกันด้วย `.gitignore` และขั้นตอน Review

หากยังตรวจไม่ครบหรือมีข้อสงสัย ให้เปลี่ยนเป็น Private ชั่วคราวทันที

### Q-004 ข้อมูลแต่ละประเภทต้องเก็บไว้นานเท่าไร?

**คำตอบจาก Stakeholder:** กำหนดระยะเก็บข้อมูลหลักเป็น **6 ปีนับจากวันที่ปิดรอบทุน** สำหรับข้อมูลผู้สมัคร เอกสารประกอบ คะแนน ความคิดเห็น ประวัติการนำเข้า Result Summary และ Audit Log

ข้อกำหนดเสริม:

- ไฟล์ Export ชั่วคราวก่อนปิดรอบ: เก็บไม่เกิน 30 วัน
- Final Report Snapshot หลังปิดรอบ: เก็บ 6 ปี
- Backup แบบหมุนเวียน: เก็บอย่างน้อย 90 วัน หรือตามนโยบายหน่วยงาน
- เมื่อครบกำหนดให้ลบอย่างปลอดภัย เว้นแต่มีคำสั่ง Legal Hold หรือข้อกำหนดของมหาวิทยาลัย

# 2. สูตรคะแนนและเกณฑ์การประเมิน

### Q-005 คะแนนในตัวเลือกเป็นคะแนนจริงอยู่แล้วหรือไม่?

**คำตอบจาก Stakeholder:** ใช่ ใช้แบบ **Embedded Point** คะแนนของตัวเลือกเป็นคะแนนที่นำไปรวมได้ทันที ห้ามคูณ `weight_percent` ซ้ำอีกครั้ง

### Q-006 คะแนนรวมของอาจารย์หนึ่งคนคำนวณอย่างไร?

**คำตอบจาก Stakeholder:** บวกคะแนนจากเกณฑ์ที่มีผลต่อคะแนนทั้ง 10 หัวข้อ ได้คะแนนเต็ม 100 คะแนน เฉพาะ Evaluation สถานะ `Submitted` เท่านั้นจึงจะถือเป็นคะแนนที่ใช้สรุปผลได้

### Q-007 คะแนนสรุปของผู้สมัครใช้ค่าเฉลี่ยธรรมดาหรือไม่?

**คำตอบจาก Stakeholder:** ใช่ ใช้ค่าเฉลี่ยเลขคณิตของคะแนนรวมจากผู้ประเมินที่ไม่ซ้ำกัน 2–3 คน และให้น้ำหนักผู้ประเมินทุกคนเท่ากัน เช่น 80 และ 90 ได้ 85 หากคนที่ 3 Submit ต้องคำนวณใหม่จากทั้ง 3 คน

### Q-008 ปัดคะแนนตรงจุดใดและปัดอย่างไร?

**คำตอบจาก Stakeholder:** เก็บค่าระหว่างคำนวณเต็มความละเอียด ไม่ปัดคะแนนรายเกณฑ์และไม่ปัดคะแนนรวมรายผู้ประเมิน ปัดเฉพาะคะแนนสรุปของผู้สมัครเป็นทศนิยม 2 ตำแหน่งด้วย `ROUND_HALF_UP`

### Q-009 ใช้เกณฑ์ 10 หัวข้อ รวม 100 คะแนนหรือไม่?

**คำตอบจาก Stakeholder:** ใช่ ให้ใช้เกณฑ์ 10 หัวข้อ รวม 100 คะแนนเป็น Template รุ่นแรก เกณฑ์ที่เป็นข้อมูลประกอบ เช่น มูลค่าทุนที่เสนอและความคิดเห็น ไม่รวมใน 100 คะแนน

### Q-010 ชื่อเกณฑ์ที่ซ้ำกันควรใช้ชื่อใด?

**คำตอบจาก Stakeholder:** อนุมัติชื่อดังนี้ และให้ใช้ `criterion_code` เป็นตัวระบุหลักเพื่อไม่พึ่งชื่อข้อความ

1. `การสนับสนุนค่าใช้จ่ายประจำวัน`
2. `ระดับค่าใช้จ่ายประจำวันต่อเดือน`

### Q-011 หัวข้อดุลพินิจของอาจารย์กรอกคะแนนอย่างไร?

**คำตอบจาก Stakeholder:** อนุญาตคะแนนจำนวนเต็ม 0–10 ทุกค่า โดยหน้าจอควรมีค่ามาตรฐานที่เลือกง่าย และอนุญาต Custom Score ได้

- ถ้าเลือกค่ามาตรฐานตามเกณฑ์ ไม่บังคับเหตุผลรายข้อ
- ถ้าใช้ Custom Score ที่ไม่อยู่ในค่ามาตรฐาน ต้องระบุเหตุผลก่อน Submit
- ระบบไม่รับทศนิยมในหัวข้อนี้

### Q-012 ความคิดเห็นหรือเหตุผลต้องบังคับกรอกเมื่อใด?

**คำตอบจาก Stakeholder:** ไม่บังคับความคิดเห็นรวมทุกครั้งก่อน Submit แต่บังคับเหตุผลในกรณีต่อไปนี้

- ใช้ Custom Score หรือคะแนนนอกตัวเลือกมาตรฐาน
- เสนอจำนวนเงินทุนเอง
- ขอ Reopen, Cancel, Override หรือแก้ข้อมูลหลังเริ่มประเมิน
- เกณฑ์ใดกำหนด `comment_required=true`

การให้คะแนนสูงสุดหรือต่ำสุดไม่ต้องบังคับเหตุผลโดยอัตโนมัติ เว้นแต่เกณฑ์นั้นกำหนดไว้


### Q-013 มูลค่าทุนที่สมควรได้รับมีผลต่อคะแนนหรือไม่?

**คำตอบจาก Stakeholder:** ไม่มีผลต่อคะแนน 100 คะแนน ให้เก็บเป็นข้อมูลประกอบการพิจารณาแยกต่างหาก

- เพดานทุนกำหนดในระดับรอบทุนหรือประเภททุน
- ผู้ประเมินสามารถเลือกจำนวนมาตรฐานหรือกรอกจำนวนเองได้
- จำนวนที่กรอกต้องไม่เกินเพดานและต้องระบุเหตุผลเมื่อใช้ Custom Amount


### Q-014 เกณฑ์ต้องถูกล็อกตั้งแต่เมื่อไร?

**คำตอบจาก Stakeholder:** ล็อก Criteria Version เมื่อมี Evaluation แรกถูกสร้าง ไม่ว่าจะเป็น Draft หรือ Submitted หลังจากนั้นห้ามแก้ชื่อ ช่วงคะแนน ตัวเลือก น้ำหนัก หรือสูตรของ Version เดิม

หากต้องเปลี่ยน ให้สร้าง Version ใหม่ และผลเดิมต้องอ้างอิง Version เดิมตลอดเพื่อให้ตรวจสอบย้อนหลังได้

# 3. การแก้ไข ยกเลิก และเปิดรอบใหม่

### Q-015 ใครสามารถขอเปิดแก้ไขผลหลัง Submit?

**คำตอบจาก Stakeholder:** อาจารย์เจ้าของ Evaluation เป็นผู้ร้องขอหลัก เจ้าหน้าที่งานทุนสามารถสร้างคำขอแทนได้เมื่อมีเหตุจำเป็น แต่ต้องระบุว่าเป็นการดำเนินการแทนใครและเพราะเหตุใด ผู้ดูแลระบบไม่ควรเปิดแก้เองโดยไม่มีคำขอ


### Q-016 ใครอนุมัติการเปิดแก้ไข?

**คำตอบจาก Stakeholder:** ให้หัวหน้างานทุนหรือผู้ที่ได้รับมอบหมายเป็น Approver ผู้ดูแลระบบมีหน้าที่ดำเนินการทางเทคนิคหลังได้รับอนุมัติ ไม่ควรเป็นทั้งผู้ขอและผู้อนุมัติรายการเดียวกัน

ต้องมีเหตุผล เลขอ้างอิงคำขอ ผู้อนุมัติ วันเวลา และ Snapshot คะแนนเดิม


### Q-017 เปิดแก้ไขผลได้ถึงเมื่อไร?

**คำตอบจาก Stakeholder:** เปิดแก้ไข Evaluation ได้เฉพาะก่อนรอบทุนปิด หากรอบปิดแล้วต้องใช้กระบวนการ Reopen Round ตาม Q-020 ไม่อนุญาตให้แก้ผลเฉพาะรายแบบเงียบ ๆ หลังปิดรอบ

เมื่อ Reopen Evaluation แล้ว ให้สถานะกลับเป็น Draft เก็บ Revision เดิม และคำนวณ Summary ใหม่เมื่อ Submit อีกครั้ง


### Q-018 อาจารย์ยกเลิก Draft ของตนเองได้หรือไม่?

**คำตอบจาก Stakeholder:** ได้ และคืนช่องผู้ประเมินทันที รายการเดิมเปลี่ยนเป็น `Cancelled` ไม่ลบออกจากฐานข้อมูล ต้องบันทึกเหตุผลและ Audit Log

Submitted ห้าม Cancel โดยตรง ต้องผ่าน Reopen Policy


### Q-019 ปิดรอบได้หรือไม่เมื่อมีผู้สมัครประเมินไม่ครบ 2 คน?

**คำตอบจาก Stakeholder:** ระบบต้องแสดงคำเตือนและสรุปรายชื่อผู้สมัครที่ยังไม่ครบ แต่อนุญาตให้ปิดรอบได้เมื่อผู้ดูแลยืนยันอีกครั้งและระบุเหตุผล ผู้สมัครที่มี Submitted น้อยกว่า 2 คนให้เป็น `Closed Incomplete` และไม่มี Final Score

เหตุผลที่ไม่ควร Blocking ทั้งหมด คือ Proposal รองรับกรณีรอบสิ้นสุดแต่ผลไม่ครบอยู่แล้ว


### Q-020 อนุญาตให้เปิดรอบที่ปิดแล้วกลับเป็น Open หรือไม่?

**คำตอบจาก Stakeholder:** อนุญาตเฉพาะกรณีพิเศษ และไม่อนุญาตเมื่อรอบเป็น `Archived`

- ผู้ร้องขอ: หัวหน้างานทุนหรือ System Owner
- ผู้อนุมัติ: ผู้มีอำนาจที่คณะกำหนด และควรมีอาจารย์ที่ปรึกษาหรือคณะกรรมการรับทราบ
- ต้องมีเหตุผล เลขอ้างอิง และ Audit
- รายงานเดิมเก็บเป็น Immutable Snapshot และทำเครื่องหมาย `Superseded`
- เมื่อมีการ Submit/แก้ไขใหม่ ต้องคำนวณ Result Summary และรายงานใหม่

# 4. การเปิดรอบทุนและประเภททุน

### Q-021 เปิดรอบทุนได้หรือไม่หากยังไม่มีผู้สมัคร?

**คำตอบจาก Stakeholder:** ไม่ได้ ให้เป็น Blocking Error ก่อนเปลี่ยน `Draft → Open` ต้องมีผู้สมัครอย่างน้อย 1 คน มี Active Criteria Set และผ่าน Pre-open Validation


### Q-022 หลังเปิดรอบแล้วนำเข้าหรือแก้ข้อมูลผู้สมัครเพิ่มได้หรือไม่?

**คำตอบจาก Stakeholder:** อนุญาตให้นำเข้าผู้สมัครรายใหม่ระหว่างรอบ Open ได้ โดยต้องผ่าน Preview/Validation ตามปกติ

สำหรับผู้สมัครเดิม:

- หากยังไม่มี Evaluation: Admin แก้หรือ Import Update ได้
- หากมี Evaluation แล้ว: ห้ามแก้ข้อมูลที่มีผลต่อคะแนนผ่าน Import ปกติ ต้องใช้ Controlled Correction พร้อมเหตุผลและ Audit
- เพิ่มเอกสารหรือแก้ข้อมูลติดต่อที่ไม่กระทบคะแนนได้ตามสิทธิ์


### Q-023 นักศึกษาคนเดียวสมัครมากกว่า 1 ประเภททุนในรอบเดียวได้หรือไม่?

**คำตอบจาก Stakeholder:** ให้รองรับได้ เพราะเป็นโครงสร้างที่ยืดหยุ่นกว่าและป้องกันการแก้ฐานข้อมูลครั้งใหญ่ในอนาคต แต่แต่ละใบสมัครต้องเป็นรายการแยกและมีการประเมินแยกตามประเภททุน


### Q-024 Business Key ควรเป็นอะไรเมื่อสมัครหลายประเภททุน?

**คำตอบจาก Stakeholder:** ใช้ `scholarship_round_id + scholarship_type_id + student_id` เป็น Business Unique Key และใช้ UUID เป็น Primary Key ภายในระบบ

# 5. ข้อมูลผู้สมัครและการนำเข้าไฟล์

### Q-025 ฟิลด์ใดต้องมีตอน Import และก่อนประเมิน?

**คำตอบจาก Stakeholder:** แบ่งเป็น 3 กลุ่มดังนี้

**1) Hard Required ตอน Import**

- รหัสนักศึกษา
- ชื่อ
- นามสกุล
- คณะ
- สาขา
- ชั้นปี
- ประเภททุน เมื่อรอบรองรับหลายประเภททุน

**2) ว่างได้ตอน Import แต่ต้องครบก่อนเริ่ม Evaluation**

- คำนำหน้า
- วันที่สมัคร
- GPA
- เบอร์โทรหรืออีเมลอย่างน้อยหนึ่งอย่าง
- ข้อมูลและเอกสารที่ใช้ตอบเกณฑ์ประเมินหลักของรอบนั้น
- สถานะการตรวจสอบข้อมูลโดย Admin

**3) Optional**

- พิกัดบ้าน
- รายละเอียดอุปกรณ์อิเล็กทรอนิกส์
- ข้อมูลประวัติบางรายการที่ไม่มีในปีนั้น
- หมายเหตุเพิ่มเติม

ระบบต้องให้แต่ละรอบกำหนด `required_before_evaluation` เพิ่มได้โดยไม่ต้องแก้ Code


### Q-026 วันที่สมัครเป็นข้อมูลบังคับหรือไม่?

**คำตอบจาก Stakeholder:** ว่างได้ในขั้น Upload/Preview แต่ต้องครบและผ่าน Validation ก่อนเปิดให้ผู้ประเมินเริ่ม Evaluation


### Q-027 ต้องมีเบอร์โทรหรืออีเมลอย่างน้อยหนึ่งอย่างหรือไม่?

**คำตอบจาก Stakeholder:** ต้องมีอย่างน้อยหนึ่งอย่าง ไม่บังคับว่าต้องมีทั้งสองอย่าง ระบบต้องแสดง Warning หากมีเพียงช่องเดียว แต่ไม่ถือเป็น Error


### Q-028 รหัสนักศึกษาตรวจ Check Digit หรือไม่?

**คำตอบจาก Stakeholder:** รุ่นแรกตรวจเฉพาะรูปแบบ `ตัวเลข 9 หลัก-ตัวเลข 1 หลัก` และตรวจค่าซ้ำ ยังไม่ตรวจ Check Digit จนกว่าหน่วยงานข้อมูลนักศึกษาจะให้สูตรอย่างเป็นทางการและชุดข้อมูลทดสอบ


### Q-029 ช่องว่างหรือเครื่องหมาย `-` ถือว่าไม่มีข้อมูลหรือไม่?

**คำตอบจาก Stakeholder:** ใช่ หากทั้ง Cell เป็นช่องว่างหรือ `-` ให้ Normalize เป็น `NULL` ค่า `0` ต้องคงเป็นศูนย์และห้ามแปลงเป็น `NULL` หาก `-` เป็นส่วนหนึ่งของรหัสหรือข้อความ เช่น รหัสนักศึกษา ให้เก็บตามรูปแบบของฟิลด์นั้น


### Q-030 รองรับรูปแบบวันที่และเบอร์โทรใด?

**คำตอบจาก Stakeholder:** Template ใหม่กำหนดมาตรฐานดังนี้

- วันที่: `YYYY-MM-DD`
- DateTime: ISO 8601 พร้อม Timezone
- เบอร์ไทย: `0XXXXXXXXX`
- ต่างประเทศ/รูปแบบสากล: `+66XXXXXXXXX`

Legacy Import อนุญาต `DD/MM/YYYY`, วันที่ภาษาไทย, ปี พ.ศ. และ Excel Serial Date โดยต้อง Preview ค่าที่ Normalize ก่อน Confirm เบอร์โทรสามารถมีช่องว่างหรือขีดได้ แต่ระบบต้องลบเครื่องหมายก่อนตรวจรูปแบบ


### Q-031 รายได้และค่าใช้จ่ายเป็นต่อเดือนทั้งหมดหรือไม่?

**คำตอบจาก Stakeholder:** ให้กำหนดหน่วยดังนี้

- รายได้บิดา มารดา ผู้อุปการะ รายได้เสริม ค่าเช่าที่พัก และค่าใช้จ่ายส่วนตัว: ต่อเดือน
- ค่าอุปกรณ์การศึกษา: ต่อภาคการศึกษา
- ฟิลด์จำนวนเงินทุกประเภทควรมี `period` หรือหน่วยกำกับเพื่อป้องกันความเข้าใจผิด


### Q-032 รองรับไฟล์เดิมที่ผู้สมัครหนึ่งคนใช้หลายแถวถึงเมื่อไร?

**คำตอบจาก Stakeholder:** รองรับเฉพาะช่วงเปลี่ยนผ่าน ได้แก่ UAT และรอบใช้งานจริงรอบแรก หลังจากนั้นให้ใช้ Template ใหม่ที่แยก Applicant, Loan History และ Scholarship History เป็นคนละ Sheet

Importer ต้องแสดง Continuation Row และเจ้าของแถวให้ Admin ตรวจสอบก่อน Confirm


### Q-033 เมื่อพบผู้สมัครเดิมในรอบเดียวกันทำอย่างไร?

**คำตอบจาก Stakeholder:**

- ซ้ำภายในไฟล์เดียวกัน: Error และไม่ Import รายการนั้น
- ซ้ำกับฐานข้อมูลในรอบ: Default เป็น Skip
- Admin เลือก Update ได้เฉพาะเมื่อยังไม่มี Evaluation
- ห้าม Update อัตโนมัติ


### Q-034 หากอนุญาต Update ผู้สมัครเดิม แก้ฟิลด์ใดได้บ้าง?

**คำตอบจาก Stakeholder:**

**ก่อนมี Evaluation** — แก้ข้อมูลติดต่อ ที่อยู่ พิกัด รายได้ ค่าใช้จ่าย ครอบครัว เอกสาร ประวัติ กยศ. และประวัติทุนได้ โดยเก็บ Audit

**หลังมี Draft หรือ Submitted** — ห้ามแก้ข้อมูลที่ใช้ในการให้คะแนนผ่าน Import ปกติ อนุญาตเฉพาะ:

- แก้เบอร์โทร/อีเมล
- เพิ่มเอกสารใหม่โดยไม่แทนไฟล์เดิมแบบไร้ประวัติ
- แก้ความผิดพลาดเชิงธุรการผ่าน Controlled Correction พร้อมเหตุผล ผู้อนุมัติ และ Before/After

`student_id`, รอบทุน และประเภททุนห้ามแก้ด้วย Update ให้ยกเลิกรายการเดิมและสร้างใหม่เมื่อจำเป็น


### Q-035 ข้อมูล กยศ. หนึ่งปีมีหลายงวดได้หรือไม่?

**คำตอบจาก Stakeholder:** สำหรับ Release 1 ให้เก็บหนึ่งยอดรวมต่อปีการศึกษาต่อผู้สมัคร หากต้นทางมีหลายงวดให้งานทุนรวมยอดก่อน Import หรือระบบรวมยอดใน Preview พร้อมแสดงรายการต้นทาง

หากภายหลังต้องเก็บหลายงวด ให้เพิ่ม `installment_no` โดยไม่เปลี่ยนผลรวมรายปี


### Q-036 ประวัติ กยศ. และทุนเป็นข้อมูลกลางหรือ Snapshot รายรอบ?

**คำตอบจาก Stakeholder:** ให้เก็บเป็น **Snapshot แยกตามรอบทุน** เพื่อรักษาข้อมูลที่ใช้ตัดสินใจในเวลานั้น ไม่ให้การแก้ข้อมูลกลางในอนาคตเปลี่ยนหลักฐานของรอบเก่า

อาจพัฒนา Applicant Master กลางในอนาคตได้ แต่ Evaluation และ Report ต้องอ่าน Snapshot ของรอบนั้น


### Q-037 ระบบจำเป็นต้องเก็บเลขบัตรประชาชนหรือไม่?

**คำตอบจาก Stakeholder:** ไม่จำเป็นสำหรับ Core Flow ของ SEMS และไม่ให้เก็บใน Release 1 หากไม่มีหนังสือยืนยันความจำเป็น ฐานกฎหมาย ผู้มีสิทธิ์เข้าถึง ระยะเก็บ และมาตรการเข้ารหัส

หากจำเป็นในอนาคต ต้องเป็น Restricted Field แยกสิทธิ์ เข้ารหัส Mask บนหน้าจอ ไม่อยู่ใน Standard Export และไม่ใช้เป็น Primary Key


### Q-038 ต้องเก็บค่าต้นฉบับจากไฟล์ Import หรือไม่?

**คำตอบจาก Stakeholder:** Production ต้องเก็บไฟล์ต้นฉบับ Import, Hash, Raw Row, Normalized Value และ Validation Message เพื่อ Audit ภายใต้สิทธิ์ Admin เท่านั้น ระยะเก็บให้สอดคล้องกับข้อมูลหลัก 6 ปี

ห้ามนำ Raw File จริงไปใช้ใน Development/Test และต้องเข้ารหัส Storage/Backup


### Q-039 รายการค่ามาตรฐานที่ควรใช้

**คำตอบจาก Stakeholder:** งานทุนต้องเป็นผู้อนุมัติ Code List ทางการ ระบบต้องจัดการ Code List ผ่านฐานข้อมูล ไม่ Hardcode ใน Frontend โดยเริ่มต้นเสนอหมวดดังนี้

- ที่พัก: บ้านครอบครัว, หอพักมหาวิทยาลัย, หอพักเอกชน, บ้านญาติ, อื่น ๆ
- สถานภาพครอบครัว: อยู่ร่วมกัน, แยกกันอยู่, หย่าร้าง, บิดาเสียชีวิต, มารดาเสียชีวิต, ทั้งสองเสียชีวิต, ไม่ทราบ, อื่น ๆ
- ผู้รับผิดชอบค่าเทอม/ค่าใช้จ่าย: บิดามารดา, บิดา, มารดา, ตนเอง, ญาติ, ผู้อุปการะ, ทุน, เงินกู้/กยศ., อื่น ๆ
- ประเภททุน: จัดการโดย Admin ตามรอบ
- ประเภทเอกสาร: บัตรนักศึกษา, Transcript, หนังสือรับรองรายได้, ภาพถ่ายที่พัก, เอกสารครอบครัว, อื่น ๆ

ต้องมีค่า `OTHER` พร้อมช่องระบุรายละเอียด และห้ามลบ Code ที่เคยถูกใช้งาน ให้เปลี่ยนเป็น Inactive

# 6. รายงานและการส่งออกข้อมูล

### Q-040 มี Report Template จริงหรือไม่?

**คำตอบจาก Stakeholder:** ให้ขอไฟล์รายงานที่ใช้งานจริงล่าสุดจากงานทุนก่อน Freeze Template หากไม่มี ให้ทีมใช้ Template ที่เสนอใน Q-041 เป็นรุ่นแรกและนำ Prototype ให้ผู้ใช้รายงานอนุมัติ


### Q-041 Excel ใช้ 2 Sheet และ CSV แยก 2 ไฟล์หรือไม่?

**คำตอบจาก Stakeholder:** อนุมัติ

1. `Summary` — ผู้สมัครหนึ่งใบสมัครต่อหนึ่งแถว
2. `Evaluator Detail` — Evaluation หนึ่งรายการต่อหนึ่งแถว

CSV ให้แยกเป็น 2 ไฟล์และจัดส่งรวมเป็น ZIP เมื่อส่งออกพร้อมกัน


### Q-042 รายงานต้องมีข้อมูลใดและเรียงอย่างไร?

**คำตอบจาก Stakeholder:**

**Summary**

1. Round Code / Round Name
2. Scholarship Type
3. Student ID
4. ชื่อ-นามสกุล
5. คณะ / สาขา / ชั้นปี
6. Submitted Count
7. Applicant Evaluation Status
8. Total Score ของผู้ประเมินคนที่ 1–3
9. Latest/Final Score
10. มูลค่าทุนที่เสนอ
11. Finalized At / Updated At

**Evaluator Detail**

1. Round / Scholarship Type
2. Student ID / ชื่อผู้สมัคร
3. Evaluator ID และชื่อสำหรับ Internal Report
4. Criteria Version
5. คะแนนรายเกณฑ์
6. Total Score
7. ความคิดเห็นและมูลค่าทุนที่เสนอ
8. Evaluation Status / Submitted At

การเรียง Standard Summary: Final Score มากไปน้อย จากนั้น Student ID น้อยไปมาก และ `Closed Incomplete` อยู่ท้าย ไม่ส่งออกเลขบัตรประชาชนและข้อมูลติดต่อโดยค่าเริ่มต้น


### Q-043 รายงานแสดงชื่อผู้ประเมินและความคิดเห็นหรือไม่?

**คำตอบจาก Stakeholder:** ให้มี 2 Template

- `INTERNAL_FULL` — Admin/งานทุนเห็นชื่อผู้ประเมิน คะแนนและความคิดเห็นครบ
- `SUMMARY_MASKED` — ปกปิดชื่อผู้ประเมินและไม่แสดงความคิดเห็นรายบุคคล ใช้สำหรับส่งต่อวงกว้าง

Evaluator ไม่สามารถ Export ผลของผู้ประเมินคนอื่น


### Q-044 เมื่อข้อมูลเปลี่ยนหลัง Export ต้องเก็บ Snapshot หรือไม่?

**คำตอบจาก Stakeholder:** ทุก Export ต้องมี Audit Metadata และ File Hash รายงานระหว่างรอบให้สร้างจากข้อมูลล่าสุดเสมอและเก็บไฟล์ชั่วคราว ส่วนรายงาน Final หลังปิดรอบให้เก็บ Immutable Snapshot

หากเปิดรอบใหม่ รายงาน Final เดิมต้องคงอยู่และถูกทำเครื่องหมาย `Superseded` ไม่เขียนทับ


### Q-045 ไฟล์รายงานเก็บบน Server นานเท่าไร?

**คำตอบจาก Stakeholder:**

- Interim Export: 30 วัน แล้วลบไฟล์ แต่เก็บ Audit Metadata
- Final Report Snapshot: 6 ปี
- ผู้ใช้สามารถสั่งสร้างใหม่จากข้อมูลล่าสุดตามสิทธิ์
- Link ดาวน์โหลดต้องมีอายุสั้นและผ่าน Backend Authorization

# 7. KKU SSO บัญชีผู้ใช้ และความปลอดภัย

### Q-046 ใครประสานงานลงทะเบียน Application กับ KKU OAuth/OIDC?

**คำตอบจาก Stakeholder:** ให้อาจารย์ที่ปรึกษาหรือผู้รับผิดชอบระบบของคณะเป็นผู้เปิดเรื่องอย่างเป็นทางการกับ Office of Digital Technology/KKU IT ทีมพัฒนาเตรียมเอกสาร Architecture, Environment, Redirect URI, Claims และผู้รับผิดชอบ Client Secret

ห้ามให้นักศึกษาถือ Production Client Secret เป็นผู้รับผิดชอบเพียงคนเดียวหลังส่งมอบ


### Q-047 Redirect URI และ Logout URI คืออะไร?

**คำตอบจาก Stakeholder:** ให้แยก OAuth Client ต่อ Environment และห้ามใช้ Wildcard

รูปแบบที่เสนอ:

- Development: URL ที่ KKU IT อนุญาตสำหรับ Development Client
- UAT: `https://<uat-domain>/auth/kku/callback`
- Production: `https://<production-domain>/auth/kku/callback`
- Post Logout: `https://<domain>/logged-out`

ค่าจริงต้องกำหนดหลังได้รับ Domain และต้องตรงกับรายการที่ลงทะเบียนทุกตัวอักษร


### Q-048 KKU SSO ส่ง Claims ใดให้ระบบ?

**คำตอบจาก Stakeholder:** SEMS ต้องการ `sub` เป็นตัวระบุถาวร และต้องการชื่อกับอีเมลสำหรับแสดงผล ส่วนรหัสบุคลากร หน่วยงาน และสถานะบัญชีให้ใช้เมื่อ KKU มี Claim อย่างเป็นทางการเท่านั้น

Minimum Claims:

- `sub` — Required
- `name` หรือ `given_name`/`family_name`
- `email`
- `personnel_id` — Optional จนกว่าจะยืนยัน
- `organization/faculty` — Optional

ห้ามอาศัย Email เป็น Primary Identity หากมี `sub`


### Q-049 บัญชี SEMS สร้างล่วงหน้าหรืออัตโนมัติ?

**คำตอบจาก Stakeholder:** ผู้ดูแลสร้างหรือเชื่อมบัญชีและกำหนด Role ล่วงหน้า เมื่อ Login ครั้งแรกระบบจึงเชื่อม KKU `sub` กับบัญชีที่ได้รับอนุญาต ไม่ให้ผู้ใช้ใหม่ได้สิทธิ์อัตโนมัติ

หากไม่พบ Account ให้แสดง `USER_NOT_PROVISIONED` และช่องทางติดต่อ Admin


### Q-050 Logout ออกจาก SEMS หรือ KKU SSO ทั้งหมด?

**คำตอบจาก Stakeholder:** ค่าเริ่มต้นให้ออกจาก SEMS เฉพาะ Application และยกเลิก SEMS Session เพื่อไม่รบกวนระบบ KKU อื่น ให้มีตัวเลือก “ออกจากระบบ KKU ทั้งหมด” เฉพาะเมื่อ KKU IT รองรับและผู้ใช้ยืนยันชัดเจน


### Q-051 Session หมดอายุเมื่อใด?

**คำตอบจาก Stakeholder:**

- Idle Timeout: 30 นาที
- Absolute Session Lifetime: 8 ชั่วโมง
- Session Cookie: `HttpOnly`, `Secure`, `SameSite` ที่เหมาะสม
- Admin ต้องสามารถ Revoke Session ได้
- เมื่อ SEMS Account ถูก Inactive ให้ตัดสิทธิ์ในการเรียก API ครั้งถัดไปทันที
- เมื่อ KKU Account ถูกระงับ ให้ตัด Session เดิมทันทีเมื่อระบบได้รับสัญญาณจาก KKU; หากไม่มีช่องทางแจ้งทันที ให้ตรวจใหม่ตาม Token/Introspection Policy และไม่เกิน Absolute Lifetime


### Q-052 Evaluator เห็นข้อมูลผู้ประเมินคนอื่นแค่ไหน?

**คำตอบจาก Stakeholder:** เห็นเฉพาะจำนวน Slot/Submitted เช่น `2/3` และสถานะว่าครบขั้นต่ำหรือไม่ ไม่เห็นชื่อ คะแนน ความคิดเห็น หรือมูลค่าทุนที่ผู้ประเมินคนอื่นเสนอ Evaluator เห็นรายละเอียดเฉพาะ Evaluation ของตนเอง

# 8. เอกสารแนบ Server และการดูแลระบบ

### Q-053 จำกัดขนาดและชนิดไฟล์เท่าไร?

**คำตอบจาก Stakeholder:** ค่าเริ่มต้นสำหรับ Release 1

- PDF: สูงสุด 20 MB ต่อไฟล์
- JPG/PNG: สูงสุด 10 MB ต่อไฟล์
- สูงสุด 10 ไฟล์ต่อผู้สมัคร
- ไม่อนุญาตไฟล์ Executable, Archive, Office Macro หรือไฟล์ที่ MIME ไม่ตรง Extension
- Import XLSX/CSV: สูงสุด 20 MB ต่อ Batch

ค่าทั้งหมดต้อง Config ได้โดยไม่แก้ Code

### Q-054 ต้องตรวจ Malware หรือไม่?

**คำตอบจาก Stakeholder:** ต้องตรวจทุกไฟล์ใน Production ก่อนเปิดให้ผู้ใช้อื่นดาวน์โหลดหรือดู หากระบบสแกนไม่พร้อม ให้เก็บไฟล์ใน Quarantine และไม่ถือว่า Upload สำเร็จจนผ่านการตรวจ

Development/Test ใช้ไฟล์จำลองและอย่างน้อยต้องตรวจ MIME, Extension และ Signature ของไฟล์



### Q-055 ระบบจะติดตั้งที่ใด?

**คำตอบจาก Stakeholder:** เป้าหมาย Production คือ Server ของคณะหรือมหาวิทยาลัย Cloud ใช้สำหรับ Development/UAT/สาธิตเป็นแผนสำรอง หาก Production Server ยังไม่พร้อม

ก่อน Production ต้องยืนยัน:

- Domain และ HTTPS Certificate
- PostgreSQL
- Private File/Object Storage
- Secret Management
- Backup/Monitoring
- ผู้รับผิดชอบค่าใช้จ่ายและสิทธิ์ Admin


### Q-056 ความพร้อมใช้งานและจำนวนผู้ใช้พร้อมกันเท่าไร?

**คำตอบจาก Stakeholder:** กำหนด Capacity Baseline สำหรับออกแบบและ Load Test รุ่นแรกดังนี้

- Admin/งานทุน: ไม่เกิน 5 บัญชี
- Evaluator ทั้งหมด: รองรับอย่างน้อย 100 บัญชี
- Concurrent Users: อย่างน้อย 50 คน
- ผู้สมัคร: อย่างน้อย 1,000 รายต่อรอบ
- เอกสาร: สูงสุด 10 ไฟล์ต่อผู้สมัคร ค่าเฉลี่ยประมาณ 5 MB ต่อไฟล์
- ระบบควรรองรับการเลือกผู้สมัครพร้อมกันโดยไม่ให้เกิน 3 Evaluations

ตัวเลขจริงต้องตรวจจากสถิติ 3 ปีย้อนหลังของงานทุน

### Q-057 Backup ต้องมี RPO/RTO เท่าไร?

**คำตอบจาก Stakeholder:**

- RPO: ไม่เกิน 24 ชั่วโมง
- RTO: ไม่เกิน 8 ชั่วโมงในวันทำการ
- Database Backup: ทุกวัน และ Full Backup อย่างน้อยสัปดาห์ละครั้ง
- File Storage Backup: ต้องสอดคล้องกับ Database เพื่อไม่ให้ข้อมูลอ้างอิงขาด
- ผู้รับผิดชอบ Backup: ผู้ดูแล Server/Infrastructure
- ผู้มีสิทธิ์ Restore: ผู้ดูแล Infrastructure และ Database ที่ได้รับมอบหมาย
- Restore Test: อย่างน้อยทุก 3 เดือนและก่อน Production Go-live

# 9. การทดสอบ การอนุมัติ และการใช้งานจริง

### Q-058 ใครเป็นตัวแทน UAT และทดสอบช่วงใด?

**คำตอบจาก Stakeholder:** ผู้ทดสอบขั้นต่ำ

- อาจารย์ผู้ประเมินอย่างน้อย 2 คน
- เจ้าหน้าที่งานทุน/Admin อย่างน้อย 2 คน
- ผู้ดูแลระบบหรือ IT อย่างน้อย 1 คนสำหรับ Deployment/Backup Scenario

ช่วงทดสอบตามแผนโครงการ: 18 มกราคม–14 กุมภาพันธ์ 2570 โดยต้องนัดวันจริงล่วงหน้าและมี UAT Script กับ Sign-off Form


### Q-059 ใครอนุมัติ Requirement Baseline และ System Design?

**คำตอบจาก Stakeholder:**

- Requirement Baseline: หัวหน้างานทุนหรือ System Owner ร่วมกับอาจารย์ที่ปรึกษา
- System Design: อาจารย์ที่ปรึกษา ผู้แทนงานทุน และผู้แทน IT/ผู้ดูแล Server
- ประเด็น PDPA/Security: เจ้าของข้อมูลหรือผู้รับผิดชอบที่หน่วยงานกำหนด

หลักฐานควรใช้บันทึกประชุมที่ระบุ Decision ID และแนบอีเมลหรือเอกสารลงนาม ไม่ควรใช้การตอบปากเปล่าอย่างเดียว

### Q-060 ขั้นตอนเดิมใช้เวลาเท่าไรในการรวมคะแนนและทำรายงาน?

**คำตอบจาก Stakeholder:** ยังไม่ควรกำหนดตัวเลขจากการคาดเดา ต้องเก็บ Baseline จริงก่อน โดยเลือกอย่างน้อย 1 รอบย้อนหลังหรือชุดข้อมูลจำลองขนาด 30–50 ผู้สมัคร วัดแยกเป็น

- เวลาเตรียมและรวมไฟล์คะแนน
- เวลาตรวจสูตร/แก้ข้อมูลผิด
- เวลาสร้างรายงาน
- จำนวนผู้ปฏิบัติงาน
- จำนวนข้อผิดพลาดหรือการแก้ซ้ำ

เป้าหมายเบื้องต้นของโครงการคือให้เวลารวมคะแนนและสร้างรายงานลดลงอย่างน้อย 50% แต่ต้องยืนยันหลังได้ Baseline

### Q-061 หลังส่งมอบใครดูแลระบบและรับแจ้งปัญหา?

**คำตอบจาก Stakeholder:** กำหนดบทบาท ไม่ผูกกับชื่อบุคคลใน Code

- System Owner: หัวหน้าหรือผู้รับผิดชอบงานทุน
- Business Admin หลัก: เจ้าหน้าที่งานทุนที่ได้รับมอบหมาย
- Server/Database/Backup: ผู้ดูแล IT ของคณะหรือมหาวิทยาลัย
- ผู้รับแจ้งปัญหา: ช่องทางกลางของหน่วยงาน เช่น Service Desk หรืออีเมลกลุ่ม
- Critical Incident: ตอบรับภายใน 1 วันทำการ
- ปัญหาทั่วไป: ตอบรับภายใน 3 วันทำการ
- ทีมผู้จัดทำรับผิดชอบแก้ไขในช่วงรับประกัน/ช่วงโครงการตามข้อตกลงส่งมอบ ไม่เป็นผู้ดูแล Production ถาวรโดยอัตโนมัติ

# 10. สรุปมติสำคัญที่สามารถนำไปปรับเอกสารได้ทันที

1. ใช้ Embedded Point รวม 10 เกณฑ์ คะแนนเต็ม 100
2. Final Score เป็นค่าเฉลี่ยเลขคณิตของ Submitted 2–3 คน น้ำหนักเท่ากัน
3. ปัดเฉพาะ Final Score 2 ตำแหน่งแบบ `ROUND_HALF_UP`
4. ล็อก Criteria Version ตั้งแต่มี Evaluation แรก
5. Evaluator ยกเลิก Draft ของตนได้ และ Reopen Submitted ต้องมีผู้อนุมัติ
6. ปิดรอบได้แม้มีผู้สมัครไม่ครบ 2 คน แต่ต้องเตือนและยืนยัน ผู้สมัครเป็น `Closed Incomplete`
7. รองรับนักศึกษาคนเดียวหลายประเภททุน โดย Business Key รวม `scholarship_type_id`
8. Duplicate Import ไม่ Update อัตโนมัติ และห้าม Update ข้อมูลคะแนนหลังมี Evaluation ผ่าน Import ปกติ
9. ไม่เก็บเลขบัตรประชาชนใน Release 1
10. ประวัติ กยศ./ทุนเก็บเป็น Snapshot ต่อรอบ
11. รายงานใช้ Summary + Evaluator Detail และมี Internal Full/Masked Template
12. Evaluator ไม่เห็นตัวตน คะแนน หรือความคิดเห็นของผู้ประเมินคนอื่น
13. บัญชี SEMS ต้อง Provision ล่วงหน้า และใช้ KKU `sub` เป็น Identity หลัก
