# Requirement Decision Register สำหรับโครงการ SEMS

| รายการ | รายละเอียด |
| :--- | :--- |
| Version | **v1.1** |
| Last Updated | **2026-07-23** |
| Author | **SEMS Requirements Team** |
| Status | **Provisional Baseline — Pending Stakeholder Ratification** |

เอกสารฉบับนี้จัดทำขึ้นเพื่อรวบรวมประเด็นความต้องการของระบบที่ต้องได้รับการยืนยันก่อนเข้าสู่ขั้นตอนออกแบบระบบ โดยแยกสถานะของแต่ละเรื่องให้ชัดเจนว่าเป็นข้อสรุปที่ยืนยันแล้ว ประเด็นที่ต้องตรวจสอบเพิ่มเติม หรือเรื่องที่ยังต้องตัดสินใจ

## ความหมายของสถานะ

- **Confirmed** — มีข้อสรุปใน Proposal หรือได้รับการยืนยันจากผู้ใช้งานแล้ว
- **Selected (Provisional)** — AI เลือกแนวทางให้ตามคำอนุญาตของผู้ใช้เพื่อใช้เป็นค่าเริ่มต้น แก้ไขได้ และยังไม่ถือว่าได้รับการรับรองจากงานทุน
- **Pending Confirmation** — มีแนวทางจากไฟล์จริงหรือข้อมูลเบื้องต้น แต่ยังต้องให้งานทุนยืนยัน
- **Open Decision** — ยังไม่มีข้อสรุป และอาจกระทบต่อการออกแบบหรือการพัฒนาระบบ

จาก Proposal มีการยืนยันกฎหลักบางส่วนแล้ว เช่น ผู้ประเมิน 2–3 คน ใช้เฉพาะผล Submitted อนุญาตผู้ประเมินคนที่ 3 ก่อนปิดรอบ และผู้สมัครที่ปิดรอบโดยมีผลไม่ครบ 2 คนจะเป็น `Closed Incomplete` โดยไม่มีคะแนนสรุปสุดท้าย ส่วนสูตร น้ำหนัก การปัดเศษ และ Reopen Policy ยังต้องยืนยันเพิ่มเติม

## บันทึกการเลือกและการแก้ไขย้อนหลัง

| Log ID | วันที่ | ผู้เลือก | ขอบเขต | ที่มาและเหตุผล | สถานะ |
|---|---|---|---|---|---|
| DL-001 | 2026-07-23 | Codex (AI) ตามคำอนุญาตโดยตรงของผู้ใช้ | RD-008–RD-022 | เลือกข้อเสนอที่มีอยู่ใน [`SEMS_Requirement_Decision_Analysis.md`](./SEMS_Requirement_Decision_Analysis.md) เป็นค่าเริ่มต้น เพื่อปิด Open/Pending โดยไม่อ้างว่าได้รับการรับรองจากงานทุน | Provisional |

## รูปแบบคอลัมน์ที่ควรมีในไฟล์ Register จริง

| คอลัมน์ | การใช้งาน |
|---|---|
| Decision ID | รหัสอ้างอิง เช่น `RD-001` |
| Category | หมวด เช่น Evaluation, Scoring, Import, Report, Security |
| Decision Question | คำถามที่ต้องตัดสินใจ |
| Current Evidence | หลักฐานจาก Proposal, Interview หรือชื่อไฟล์ตัวอย่าง |
| Proposed Decision | แนวทางที่ทีมเสนอ |
| Final Decision | ข้อสรุปที่ผู้ใช้งานอนุมัติ |
| Status | `Open`, `Pending Confirmation`, `Selected (Provisional)`, `Confirmed`, `Changed` |
| Priority | `Critical`, `High`, `Medium`, `Low` |
| Decision Owner | ผู้มีอำนาจตัดสินใจ |
| Decision Date | วันที่ยืนยัน |
| Impacted Modules | โมดูลที่ได้รับผลกระทบ เช่น Import, Evaluation, Calculation, Report |
| Notes | เหตุผล ข้อจำกัด หรือข้อมูลเพิ่มเติม |

## วิธีดำเนินงานให้เสร็จ

1. ใส่รายการทั้งหมดลง Register และแนบหลักฐานจาก Proposal การสัมภาษณ์ และไฟล์จริง
2. ส่งรายการ `Selected (Provisional)` ให้เจ้าหน้าที่งานทุนตรวจสอบ โดยให้ยืนยันหรือแก้ไขแต่ละรายการ
3. นัดประชุมยืนยันประมาณ 30–60 นาที โดยประชุมเฉพาะเรื่องที่ยังไม่มีข้อสรุป
4. บันทึกชื่อผู้อนุมัติและวันที่ในแต่ละรายการ
5. ให้ผู้รับผิดชอบงานทุนยืนยัน Requirement Baseline เป็นลายลักษณ์อักษร เช่น อีเมลหรือการลงนามในเอกสาร
6. หลังอนุมัติแล้ว เปลี่ยนสถานะเอกสารเป็น `Current` และบันทึกการอนุมัติใน Revision History

## เกณฑ์ว่าขั้นตอนนี้เสร็จสมบูรณ์

รายการระดับ `Critical` และ `High` ต้องไม่มีสถานะ `Open` โดยเฉพาะหัวข้อต่อไปนี้

- สูตรคะแนน
- การปัดเศษ
- Reopen Policy
- Unique Key
- Import Format
- Report Template

หัวข้อเหล่านี้ส่งผลโดยตรงต่อการออกแบบ ER Diagram, API, Validation Rule, Business Logic และ Test Case

Proposal กำหนด Milestone แรกเป็น `Requirement Baseline Approved` ก่อนเข้าสู่การออกแบบระบบ ดังนั้น Requirement Decision Register ควรได้รับการยืนยันก่อนเริ่มออกแบบระบบในรายละเอียด
