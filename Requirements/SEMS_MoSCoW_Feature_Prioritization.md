## 1. วัตถุประสงค์

เอกสารนี้จัดกลุ่มความสามารถของ Scholarship Evaluation Management System (SEMS) ตามวิธี MoSCoW เพื่อแสดงว่าความสามารถใดจำเป็นต่อกระบวนการทำงานหลัก (Core Flow) ความสามารถใดสามารถเลื่อนไปพัฒนาในภายหลัง และความสามารถใดอยู่นอกขอบเขตโครงการ นอกจากนี้ยังแยกข้อกำหนดสนับสนุนและการเชื่อมโยงตรวจสอบย้อนกลับออกจากตารางหลัก เพื่อให้อ่านง่ายและตรงตามข้อเสนอแนะที่ได้รับ

## 2. ขอบเขต

- ตารางหลักครอบคลุมความสามารถจาก User Story ที่ยืนยันจากคำตอบ PRD, SRS และข้อเสนอโครงการ โดยรวมรายการที่ซ้ำกันเป็นความสามารถเดียว
- ข้อกำหนดสนับสนุนและข้อกำหนดที่ไม่ใช่เชิงหน้าที่ เช่น ความปลอดภัย ความครบถ้วนของบันทึกตรวจสอบ การเก็บรักษาข้อมูล การสำรองข้อมูล ประสิทธิภาพ และขีดความสามารถ อยู่ในตารางแยกและไม่นับเป็นความสามารถของระบบ
- ข้อจำกัดด้านการออกแบบและพฤติกรรมที่ระบบต้องห้ามแยกจากความสามารถกลุ่ม Won't have เพื่อไม่ให้ทางเลือกทางเทคนิคหรือข้อห้ามถูกตีความเป็นความสามารถของระบบ
- Acceptance Criteria ใช้เป็นหลักฐานประกอบ แต่ไม่แยกเป็นความสามารถใหม่
- เอกสารนี้เป็นฉบับร่างสำหรับตรวจทาน ไม่ใช่หลักฐานอนุมัติฐานข้อกำหนด

## 3. นิยาม MoSCoW ตามข้อเสนอแนะ

| กลุ่ม | นิยามที่ใช้ |
| :--- | :--- |
| **Must have** | หากไม่มีแล้วผู้ใช้ไม่สามารถทำกระบวนการหลักตั้งแต่เข้าสู่ระบบ นำเข้าข้อมูล ประเมิน ส่งผลประเมิน คำนวณผล จนถึงส่งออกข้อมูลได้ หรือทำให้ผลลัพธ์ผิดกฎหรือเกิดช่องโหว่ร้ายแรงจนไม่สามารถนำระบบไปใช้จริงได้อย่างยอมรับได้ |
| **Should have** | สำคัญต่อการใช้งานจริง การแก้กรณียกเว้น วงจรการทำงาน การตรวจสอบย้อนหลัง หรือการดูแลระบบ แต่กระบวนการปกติยังทำงานครบและสามารถเลื่อนไปพัฒนาในรุ่นถัดไปได้ |
| **Could have** | เพิ่มความสะดวกหรือประสบการณ์ใช้งาน และมีวิธีพื้นฐานหรือการดำเนินการด้วยตนเองรองรับอยู่แล้ว โดยไม่กระทบกฎทางธุรกิจหรือผลคะแนน |
| **Won't have** | เป็นความสามารถที่เอกสารระบุว่าไม่ทำในโครงการหรือ Release 1 หรือต้องดำเนินการเป็นโครงการหรือขออนุมัติแยกต่างหาก |

## 4. วิธีพิจารณาความสามารถ

1. พิจารณาก่อนว่าเมื่อไม่มีความสามารถนั้น กระบวนการหลักส่วนใดจะหยุดหรือผลลัพธ์ใดจะผิด หากไม่มีผลดังกล่าวจะไม่จัดเป็น Must have เพียงเพราะอยู่ใน PRD หรือ Release 1
2. ใช้ลำดับความสำคัญใน User Story เป็นค่าเริ่มต้น แล้วตรวจซ้ำกับ PRD, SRS, Decision Register รวมถึงการพึ่งพา ความปลอดภัย และความถูกต้องของข้อมูล
3. รวมมาตรการควบคุมทางเทคนิคที่เป็นส่วนประกอบของความสามารถเดียวกัน ไม่แยกย่อยจนจำนวน Must have สูงขึ้นจากรายละเอียดทางเทคนิค
4. แยกกรณีผิดพลาดหรือกรณียกเว้นที่เลื่อนได้เป็น Should have แม้ SRS บางรายการระบุ Must have และบันทึกข้อขัดแย้งไว้ให้ยืนยัน
5. ใช้ Could have เฉพาะรายการที่เอกสารระบุว่าเป็นทางเลือก เป็นสิ่งที่ทำได้ก็ดี หรือทำเมื่อมีเวลา หรือมีวิธีพื้นฐานหรือการดำเนินการด้วยตนเองทดแทนได้
6. ใช้ Won't have เฉพาะความสามารถที่ตกลงไม่ทำจริง ส่วนข้อห้ามและทางเลือกด้านการออกแบบอยู่ในหัวข้อแยก
7. เก็บ Story ID, Requirement ID, Decision ID และ Trace ID ไว้ในตารางการเชื่อมโยงและตรวจสอบย้อนกลับเท่านั้น

## 5. ตารางความสามารถของระบบตาม MoSCoW

ตารางแบ่งตามกลุ่ม MoSCoW เพื่อให้ตรวจสอบแต่ละกลุ่มได้ง่าย ภายในแต่ละกลุ่มเรียงตามกระบวนการทำงานหลักของระบบ ส่วน Won't have เรียงตามประเภทของความสามารถที่อยู่นอกขอบเขต การเปลี่ยนลำดับไม่ได้หมายถึงการเปลี่ยนลำดับความสำคัญหรือขอบเขต

### 5.1 Must have

| Feature | กลุ่ม | เหตุผลที่จัดไว้กลุ่มนี้ |
| :--- | :---: | :--- |
| เข้าสู่ระบบด้วยบัญชี KKU ผ่าน OAuth/OIDC | Must have | หากไม่มี ผู้ใช้ทุกบทบาทจะเริ่มใช้งาน SEMS ไม่ได้ จึงไม่สามารถนำเข้าข้อมูล ประเมิน หรือส่งออกข้อมูลได้ |
| ควบคุมสิทธิ์ด้วย RBAC ตามบทบาท รอบทุน และความเป็นเจ้าของข้อมูล | Must have | หากไม่มี ผู้ประเมินอาจอ่านหรือแก้ผลของผู้อื่น และผู้ไม่มีสิทธิ์อาจเรียกใช้ขั้นตอนสำหรับผู้ดูแลระบบได้ ทำให้ระบบไม่ปลอดภัยพอสำหรับข้อมูลผู้สมัคร |
| ออกจากระบบ SEMS และยกเลิกวาระการใช้งาน | Must have | หากวาระการใช้งานเดิมยังใช้ได้หลังออกจากระบบ ผู้อื่นบนอุปกรณ์ที่ใช้ร่วมกันอาจเข้าถึงข้อมูลและผลประเมินต่อได้ ซึ่งเป็นช่องโหว่ร้ายแรง |
| ค้นหาและดูบัญชี SEMS | Must have | ผู้ดูแลระบบต้องค้นหาบัญชีเพื่อเชื่อมตัวตน กำหนดบทบาท และแก้สถานะ มิฉะนั้นผู้ประเมินจะไม่ได้รับสิทธิ์เข้าสู่กระบวนการหลักอย่างควบคุม |
| เตรียมบัญชีล่วงหน้า เชื่อมตัวตน KKU และกำหนดบทบาท | Must have | การเข้าสู่ระบบเพียงอย่างเดียวยังไม่ให้สิทธิ์ใช้งาน ผู้ใช้ต้องเชื่อมกับบัญชีและบทบาทก่อนจึงจะเข้าถึงกระบวนการหลักได้ |
| เปิดหรือปิดสิทธิ์บัญชี SEMS | Must have | หากบัญชีที่ถูกถอนสิทธิ์ยังเรียก API ได้ ระบบจะเปิดให้ผู้ไม่มีอำนาจเข้าถึง PII และคะแนน จึงใช้งานจริงไม่ได้อย่างยอมรับได้ |
| สร้างรอบทุน | Must have | ข้อมูลผู้สมัคร เกณฑ์ การประเมิน และรายงานต้องผูกกับรอบทุน หากไม่มีจะเริ่มและแยกกระบวนการประเมินแต่ละรอบไม่ได้ |
| แก้ไข ตรวจความพร้อม และเปิดรอบทุน | Must have | ผู้ประเมินสร้างแบบประเมินฉบับร่างได้เฉพาะรอบสถานะ `OPEN` ที่มีผู้สมัครและชุดเกณฑ์ที่เปิดใช้ หากไม่มีขั้นเปิดรอบ กระบวนการประเมินจะเริ่มไม่ได้ |
| อัปโหลด `.xlsx`/`.csv` และจับคู่คอลัมน์ | Must have | เป็นช่องทางนำข้อมูลผู้สมัครเข้าสู่ระบบ หากไม่มีจะไม่มีข้อมูลสำหรับเปิดรอบ เลือกผู้สมัคร หรือประเมิน |
| แสดงตัวอย่าง ปรับรูปแบบ และตรวจสอบข้อมูลก่อนนำเข้า | Must have | หากข้ามขั้นนี้ รหัสระบุ วันที่ หรือข้อมูลบังคับอาจผิดและถูกใช้ต่อในการประเมิน ทำให้ข้อมูลและผลลัพธ์หลักไม่น่าเชื่อถือ |
| ยืนยันการนำเข้าแบบครบทั้งชุดและเก็บประวัติชุดข้อมูล | Must have | หากการยืนยันไม่ทำเป็นชุดเดียว อาจเกิดข้อมูลผู้สมัครเพียงบางส่วนหรือข้อมูลซ้ำ ทำให้กระบวนการหลักใช้ข้อมูลที่ไม่สอดคล้องกัน |
| รองรับผู้สมัครหนึ่งคนสมัครหลายประเภททุนในรอบเดียว | Must have | กุญแจข้อมูลที่ยืนยันใช้แยกใบสมัครตามประเภททุน หากไม่มี ข้อมูล เอกสาร การประเมิน และคะแนนของแต่ละทุนอาจถูกทับหรือรวมผิด |
| ดูและจัดการข้อมูลผู้สมัครกับประวัติทุน/กยศ. โดยใช้สำเนาข้อมูลของแต่ละรอบ | Must have | ผู้ประเมินต้องใช้ข้อมูลประกอบที่ผูกกับรอบเพื่อให้คะแนน หากไม่มีหน้าข้อมูลนี้ การประเมินจะขาดหลักฐานหลัก |
| ตรวจข้อมูลบังคับก่อนเริ่มประเมิน | Must have | หากสร้างแบบประเมินฉบับร่างจากข้อมูลสำคัญที่ไม่ครบ ผู้ประเมินอาจให้คะแนนจากข้อมูลที่ขาดและทำให้ผลสรุปคะแนนผิดวัตถุประสงค์ |
| อัปโหลดเอกสารผู้สมัคร | Must have | เอกสารเป็นข้อมูลประกอบที่ผู้ประเมินต้องใช้ตามขอบเขตโครงการ หากไม่มีการอัปโหลด กระบวนการประเมินหลักจะขาดหลักฐานที่กำหนด |
| แสดงตัวอย่างหรือดาวน์โหลดเอกสารตามสิทธิ์ | Must have | หากผู้ประเมินเปิดเอกสารที่ได้รับสิทธิ์ไม่ได้ จะประเมินข้อมูลประกอบไม่ครบ แต่หากเปิดโดยไม่ตรวจสิทธิ์ ระบบอาจเปิดเผย PII อย่างร้ายแรง |
| สร้างชุดเกณฑ์ คะแนน และช่องข้อมูลผลลัพธ์สำหรับรอบทุน | Must have | หากไม่มีเกณฑ์ ผู้ประเมินจะกรอกคะแนนไม่ได้ และระบบจะสร้างผลรวมตามสูตรไม่ได้ |
| ตรวจสอบและเปิดใช้รุ่นเกณฑ์ | Must have | แบบประเมินฉบับร่างและผลที่ส่งต้องอ้างอิงชุดเกณฑ์ที่เปิดใช้ มีข้อมูลครบ และมีคะแนนเต็มถูกต้อง หากเปิดใช้เกณฑ์ผิด ผลคะแนนหลักจะผิดตามไปด้วย |
| ล็อกรุ่นเกณฑ์ที่ใช้งานและสร้างรุ่นใหม่ | Must have | หากแก้เกณฑ์ย้อนหลังหลังมีแบบประเมินฉบับร่าง คะแนนเก่าและใหม่จะใช้กฎคนละชุดโดยตรวจสอบไม่ได้ ทำให้ผลสรุปคะแนนไม่ถูกต้อง |
| ค้นหาผู้สมัครในรอบที่เปิด | Must have | เป็นจุดเริ่มของผู้ประเมินในการเลือกผู้สมัคร หากไม่มีจะสร้างแบบประเมินฉบับร่างสำหรับรายการที่กำลังสัมภาษณ์ไม่ได้ |
| เลือกผู้สมัครและสร้างแบบประเมินฉบับร่างไม่ซ้ำ สูงสุด 3 คน | Must have | หากไม่ตรวจผู้ประเมินซ้ำและเพดาน 3 คน จำนวนข้อมูลเข้าของสูตรจะผิด และขั้นบันทึกหรือส่งผลประเมินจะเริ่มไม่ได้อย่างถูกต้อง |
| แสดงข้อมูลผู้สมัคร เอกสาร ประวัติ และเกณฑ์ในหน้าประเมิน | Must have | หากไม่มี ผู้ประเมินจะไม่เห็นข้อมูลที่ใช้ตัดสินคะแนนและต้องกลับไปใช้ระบบหรือไฟล์ภายนอก ทำให้กระบวนการประเมินไม่ครบ |
| กรอกคะแนน ความคิดเห็น และคำแนะนำภายใต้การตรวจสอบความถูกต้อง | Must have | คะแนนรายเกณฑ์เป็นข้อมูลเข้าโดยตรงของผลสรุป หากกรอกไม่ได้หรือไม่ตรวจช่วงคะแนน ระบบจะไม่มีผลหรือได้ผลผิดกฎ |

| ความถูกต้องของรายการข้อมูล การทำงานพร้อมกัน และฐานข้อมูล | Must have | การนำเข้า การเลือกผู้สมัคร การส่งผล และการคำนวณใหม่ต้องไม่เกิดข้อมูลเพียงบางส่วนหรือมีผู้ประเมินเกินเพดาน มิฉะนั้นผลคะแนนหลักจะผิด |
| ความครบถ้วนของบันทึกตรวจสอบ การปกปิดข้อมูล และ Trace ID | Must have | แม้หน้าดูบันทึกตรวจสอบจะเลื่อนได้ แต่เหตุการณ์สำคัญต้องบันทึกตั้งแต่แรกโดยเพิ่มรายการอย่างเดียว มิฉะนั้นจะสร้างหลักฐานย้อนหลังคืนไม่ได้ |

| การสำรองข้อมูล การทดสอบกู้คืน และเป้าหมาย RPO/RTO | Should have | การทำงานปกติยังดำเนินได้ แต่หากเกิดเหตุอาจกู้ข้อมูลคืนไม่ได้ จึงควรพร้อมก่อนใช้งานจริงและทดสอบการกู้คืนตามรอบ |

## 7. ข้อจำกัดด้านการออกแบบและพฤติกรรมที่ระบบต้องห้าม

รายการเหล่านี้ไม่ใช่ความสามารถกลุ่ม Won't have แต่เป็นข้อจำกัดด้านการออกแบบหรือพฤติกรรมที่ระบบต้องไม่อนุญาต

| ประเภท | รายการ | เหตุผล |
| :--- | :--- | :--- |
| ข้อจำกัดด้านการออกแบบ | เก็บไฟล์เอกสารแบบ Binary ใน PostgreSQL | แนวทางที่ยืนยันให้เก็บไฟล์ในพื้นที่ส่วนตัวหรือพื้นที่จัดเก็บวัตถุ และเก็บข้อมูลกำกับใน PostgreSQL จึงเป็นทางเลือกด้านการจัดเก็บ ไม่ใช่ความสามารถที่ผู้ใช้เสนอแล้วทีมตัดออก |
| พฤติกรรมที่ระบบต้องห้าม | แก้คะแนนหรือข้อมูลที่กระทบผลหลังส่งผลประเมิน โดยไม่มีการอนุมัติ บันทึกรุ่น หรือบันทึกตรวจสอบ | ระบบต้องปฏิเสธพฤติกรรมนี้เพื่อรักษาความถูกต้องของข้อมูล ความสามารถที่รองรับจริงคือการแก้ไขแบบควบคุมหรือการเปิดผลประเมินให้แก้ไข |

## 12. รายการที่ต้องให้ผู้มีส่วนได้ส่วนเสียหรืออาจารย์ยืนยัน

1. ลำดับความสำคัญในเอกสารต้นทางยังขัดกับการตีความตามข้อเสนอแนะสำหรับ `US-DSH-002` (User Story เป็น Must have แต่เอกสารนี้เป็น Should have), `FR-COD-001` (SRS เป็น Must have แต่เอกสารนี้เป็น Should have), การแก้ไขแบบควบคุม การเปิดรอบในกรณีพิเศษ และวงจรรายงาน ทั้งนี้ไม่ได้แก้เอกสารต้นทางโดยอัตโนมัติ
2. `US-SEL-003` ระบุ Should have แต่ SRS §12 `FR-EVA-018` ระบุ Must have เอกสารนี้คง Should have เพราะเป็นกระบวนการสำหรับกรณียกเว้น
3. SRS ใช้ `FR-EVA-017` และ `FR-EVA-018` ซ้ำระหว่าง §3.6 กับ §12 โดยมีความหมายต่างกัน ตารางตรวจสอบย้อนกลับระบุเลขหัวข้อเพื่อแยกชั่วคราว แต่ต้องแก้ ID ก่อนกำหนดฐานข้อกำหนดระดับแถว
4. `TRC-004` ยังระบุ “DB key open” แต่ `RD-015`, `RD-024`, `RD-025` ยืนยัน key แล้ว และ `TRC-017` ระบุ Audit retention ว่า open ทั้งที่ `RD-030` ยืนยันแล้ว
5. SRS ยังแสดง `FR-CRI-004` และ `FR-EVA-012` เป็น Open ขณะที่ Decision Register ระบุว่าไม่มีข้อวินิจฉัยระดับ Critical/High สำหรับ Release 1 ค้างอยู่
6. ยังไม่มีหลักฐานของผู้อนุมัติอย่างเป็นทางการ วันที่หรือลายมือชื่ออนุมัติ การมอบหมายสำหรับระบบใช้งานจริง และผลวัดจริงของ `RD-040`/`RD-045` จึงไม่กล่าวอ้างว่าอนุมัติหรือบรรลุผลแล้ว
7. National ID มีสองความหมายที่ไม่ขัดกัน คือ “รองรับ National ID” เป็น Won't have ส่วน “ปฏิเสธหรือไม่เก็บ National ID” เป็นข้อกำหนดสนับสนุนระดับ Must have ด้านความเป็นส่วนตัว
