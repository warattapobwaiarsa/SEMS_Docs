## วิธีอ่านเอกสาร

- **[ข้อมูลจากไฟล์]** หมายถึงข้อกำหนด หลักฐาน หรือลักษณะข้อมูลที่พบในเอกสารและไฟล์ตัวอย่าง
- **[ข้อเสนอแนะจาก AI]** หมายถึงตัวเลือกที่จัดทำเพิ่มเติม เนื่องจากไฟล์ยังไม่มีข้อสรุปสุดท้าย
- **[คำแนะนำหลักจาก AI]** หมายถึงแนวทางที่เหมาะสมที่สุดในมุมการออกแบบ ความถูกต้อง การตรวจสอบย้อนหลัง และความง่ายในการใช้งาน แต่ยังต้องได้รับการอนุมัติจากงานทุน

> หมายเหตุ: รายการสถานะ `Confirmed` ด้านล่างสามารถใช้เป็น Requirement Baseline ได้ทันที หากไม่มีข้อมูลใหม่ที่ขัดแย้ง ส่วนรายการ `Pending Confirmation` และ `Open Decision` ยังไม่ควรเปลี่ยนเป็น `Confirmed` จนกว่าผู้ยืนยันหลักจะอนุมัติ

# 1. รายการที่มีคำตอบจากไฟล์แล้ว

## RD-001 — จำนวนผู้ประเมิน

**[ข้อมูลจากไฟล์]** ผู้สมัครหนึ่งคนต้องมีผลประเมินจากผู้ประเมินอย่างน้อย 2 คน และมีผู้ประเมินได้สูงสุด 3 คนต่อรอบทุน

**คำตอบที่เสนอให้บันทึกใน Final Decision**

> ผู้สมัครหนึ่งคนมีผู้ประเมินขั้นต่ำ 2 คนและสูงสุด 3 คนต่อรอบทุน โดยผู้ประเมินแต่ละคนต้องไม่ซ้ำกัน

**สถานะที่เสนอ:** `Confirmed`

---

## RD-002 — การนับจำนวนผู้ประเมิน

**[ข้อมูลจากไฟล์]** Proposal กำหนดให้ตรวจสอบจำนวน Evaluation ที่ยังไม่ถูกยกเลิกก่อนสร้างรายการใหม่ ไม่ได้นับเฉพาะรายการ `Submitted` เพื่อป้องกันกรณีมี Draft หลายรายการจนเกิน 3 คน

**คำตอบที่เสนอให้บันทึกใน Final Decision**

> การควบคุมจำนวนสูงสุด 3 คนให้นับจาก Evaluation ที่ยังไม่ถูกยกเลิกทุกสถานะ ได้แก่ Draft และ Submitted ส่วนรายการที่ถูกยกเลิกไม่นับรวม

**สถานะที่เสนอ:** `Confirmed`

---

## RD-003 — ผู้ประเมินคนเดิมประเมินซ้ำ

**[ข้อมูลจากไฟล์]** ผู้ประเมินคนเดิมต้องไม่มี Evaluation ที่ยังไม่ถูกยกเลิกมากกว่าหนึ่งรายการสำหรับผู้สมัครคนเดิมในรอบทุนเดียวกัน

**คำตอบที่เสนอให้บันทึกใน Final Decision**

> กำหนด Unique Constraint เชิงธุรกิจที่ `รอบทุน + ผู้สมัคร + ผู้ประเมิน` สำหรับ Evaluation ที่ยังไม่ถูกยกเลิก เพื่อป้องกันผู้ประเมินคนเดิมประเมินผู้สมัครซ้ำ

**สถานะที่เสนอ:** `Confirmed`

---

## RD-004 — ผลที่ใช้คำนวณ

**[ข้อมูลจากไฟล์]** ระบบใช้เฉพาะ Evaluation สถานะ `Submitted` จากผู้ประเมินที่ไม่ซ้ำกัน ผล Draft หรือผลที่ถูกยกเลิกต้องไม่ถูกนำไปคำนวณ

**คำตอบที่เสนอให้บันทึกใน Final Decision**

> คะแนนรายผู้ประเมินและคะแนนสรุปใช้เฉพาะ Evaluation สถานะ `Submitted` ที่ยังไม่ถูกยกเลิกและมาจากผู้ประเมินที่ไม่ซ้ำกันเท่านั้น

**สถานะที่เสนอ:** `Confirmed`

---

## RD-005 — ผู้ประเมินคนที่ 3

**[ข้อมูลจากไฟล์]** เมื่อมีผล Submitted ครบขั้นต่ำ 2 คนแล้ว ผู้ประเมินคนที่ 3 ยังเริ่มและส่งผลเพิ่มเติมได้ หากรอบทุนยัง `Open` และจำนวน Evaluation ที่ยังไม่ถูกยกเลิกยังไม่ครบ 3 รายการ ระบบต้องคำนวณผลสรุปใหม่เมื่อคนที่ 3 Submit

**คำตอบที่เสนอให้บันทึกใน Final Decision**

> อนุญาตให้ผู้ประเมินคนที่ 3 เริ่ม บันทึก Draft และ Submit ได้ก่อนปิดรอบทุน เมื่อ Submit สำเร็จให้คำนวณ Result Summary ใหม่โดยอัตโนมัติ

**สถานะที่เสนอ:** `Confirmed`

## RD-006 — สถานะผู้สมัคร

**[ข้อมูลจากไฟล์]** Proposal ระบุสถานะ `Not Started`, `In Progress`, `Minimum Complete`, `Fully Complete`, `Finalized` และ `Closed Incomplete`

**คำตอบที่เสนอให้บันทึกใน Final Decision**

| สถานะ | เงื่อนไข |
|---|---|
| `Not Started` | ไม่มี Evaluation ที่ยังใช้งานอยู่ |
| `In Progress` | มี Evaluation ที่ยังใช้งานอยู่ แต่ Submitted น้อยกว่า 2 รายการ |
| `Minimum Complete` | Submitted ครบ 2 รายการ และรอบยัง Open |
| `Fully Complete` | Submitted ครบ 3 รายการ และรอบยัง Open |
| `Finalized` | รอบ Closed และ Submitted อย่างน้อย 2 รายการ |
| `Closed Incomplete` | รอบ Closed และ Submitted น้อยกว่า 2 รายการ |

**สถานะที่เสนอ:** `Confirmed`

## RD-007 — ปิดรอบแต่ผลไม่ครบ

**[ข้อมูลจากไฟล์]** เมื่อรอบทุนปิด หากผู้สมัครมีผล Submitted น้อยกว่า 2 รายการ ให้เป็น `Closed Incomplete` และไม่มีคะแนนสรุปสุดท้าย

**คำตอบที่เสนอให้บันทึกใน Final Decision**

> ผู้สมัครที่มีผล Submitted น้อยกว่า 2 รายการเมื่อปิดรอบทุน ต้องมีสถานะ `Closed Incomplete`; ระบบอาจแสดงคะแนนรายผู้ประเมินที่มีอยู่เพื่อการตรวจสอบ แต่ต้องไม่สร้างหรือแสดง Final Score

**สถานะที่เสนอ:** `Confirmed`

# 2. รายการที่มีข้อมูลบางส่วน แต่ยังต้องตัดสินใจ

## RD-008 — การแก้ไขหลัง Submit

**[ข้อมูลจากไฟล์]** Proposal ระบุว่าการแก้ไขหรือยกเลิกผลหลัง Submit ต้องเป็นไปตาม `Reopen Policy` และไม่อนุญาตให้แก้ไขโดยไม่มีกระบวนการอนุมัติ แต่ยังไม่ได้ระบุผู้ร้องขอ ผู้อนุมัติ ระยะเวลา และวิธีเก็บคะแนนเดิม

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก                         | แนวทาง                                                                                                                         | ข้อดี                                         | ข้อเสีย                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- | ---------------------------------------------------------- |
| A — Controlled Reopen            | ผู้ประเมินส่งคำขอพร้อมเหตุผล หัวหน้างานทุนหรือผู้ดูแลที่ได้รับมอบหมายอนุมัติ เปิดแก้ไขได้เฉพาะก่อนปิดรอบ และเก็บ Snapshot เดิม | สมดุลระหว่างความยืดหยุ่นกับการตรวจสอบย้อนหลัง | มีขั้นตอนอนุมัติเพิ่มขึ้น                                  |
| B — Admin Reopen โดยตรง          | ผู้ดูแลระบบเปิดผลให้แก้ไขตามคำร้องที่ได้รับนอกระบบ                                                                             | ใช้งานง่ายและพัฒนาเร็ว                        | หลักฐานคำขออาจไม่ครบและเสี่ยงเปิดแก้ไขโดยไม่มีเหตุผลชัดเจน |
| C — Void แล้วสร้าง Revision ใหม่ | ไม่แก้รายการเดิม แต่ยกเลิกผลเดิมและสร้าง Evaluation Revision ใหม่ที่อ้างอิงรายการเดิม                                          | Audit ชัดเจนที่สุดและไม่สูญเสียข้อมูลเดิม     | โครงสร้างระบบและหน้าจอซับซ้อนกว่า                          |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก A** โดยกำหนดกฎดังนี้

1. ผู้ร้องขอเป็นเจ้าของ Evaluation หรือผู้ดูแลระบบ
2. ผู้อนุมัติเป็นหัวหน้างานทุนหรือผู้ใช้บทบาท `Requirement/Process Approver`
3. อนุญาตก่อนรอบทุน `Closed` เท่านั้น; หลังปิดรอบต้องเปิดรอบอย่างเป็นทางการก่อน
4. บังคับกรอกเหตุผลและเลขอ้างอิงคำขอ
5. เก็บคะแนน ความคิดเห็น สถานะ ผู้แก้ไข และเวลาเดิมเป็น Revision/Audit Snapshot
6. เมื่อ Submit ใหม่ ให้คำนวณ Result Summary, Dashboard และรายงานใหม่

**ข้อความ Final Decision ที่แนะนำ**

> ผู้ประเมินสามารถร้องขอ Reopen ผล Submitted ของตนเองพร้อมเหตุผล โดยหัวหน้างานทุนเป็นผู้อนุมัติ การแก้ไขทำได้ก่อนปิดรอบเท่านั้น ระบบต้องเก็บข้อมูลก่อนแก้ไข ประวัติการอนุมัติ และคำนวณผลสรุปใหม่หลัง Submit อีกครั้ง

## RD-009 — การยกเลิก Evaluation ก่อน Submit

**[ข้อมูลจากไฟล์]** Proposal ระบุว่าการยกเลิกก่อน Submit ต้องเป็นไปตามสิทธิ์และบันทึกประวัติ อีกทั้ง Test Case กำหนดว่ารายการที่ถูกยกเลิกไม่นับรวมในจำนวนผู้ประเมินและต้องเปิดช่องให้ผู้ประเมินคนใหม่ได้ แต่ยังไม่ระบุชัดว่าใครยกเลิกได้

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — ผู้ประเมินยกเลิก Draft ของตนเอง | เจ้าของรายการยกเลิกได้ก่อน Submit พร้อมเหตุผลสั้น ๆ และคืนช่องว่างทันที | ลดภาระผู้ดูแลและเหมาะกับกรณีเลือกผู้สมัครผิด | ผู้ประเมินอาจยกเลิกโดยไม่ตั้งใจ ต้องมีหน้าต่างยืนยัน |
| B — ผู้ดูแลระบบเท่านั้น | ผู้ประเมินต้องติดต่อผู้ดูแลเพื่อยกเลิก | ควบคุมได้มาก | ทำให้กระบวนการช้าและเพิ่มภาระงานทุน |
| C — ผู้ประเมินร้องขอ ผู้ดูแลอนุมัติ | ใช้ขั้นตอนอนุมัติทุกกรณี | Audit ชัด | ขั้นตอนมากเกินความจำเป็นสำหรับ Draft ที่ยังไม่ส่ง |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก A** โดยอนุญาตเฉพาะ Evaluation สถานะ Draft และยังไม่เคย Submitted ผู้ประเมินต้องยืนยันการยกเลิกและอาจกรอกเหตุผล ระบบเปลี่ยนสถานะเป็น `Cancelled` โดยไม่ลบข้อมูลจริง และคืนช่องผู้ประเมินทันทีภายใน Transaction เดียวกัน

**ข้อความ Final Decision ที่แนะนำ**

> ผู้ประเมินสามารถยกเลิก Draft ของตนเองก่อน Submit ได้ ระบบต้องบันทึกประวัติและคืนช่องผู้ประเมินทันที รายการ Submitted ใช้ Reopen Policy และไม่สามารถยกเลิกเองได้

## RD-010 — สูตรคะแนนสรุป

**[ข้อมูลจากไฟล์]** ระบบต้องคำนวณจากผู้ประเมิน 2–3 คน โดยใช้เฉพาะผล Submitted และรองรับสูตร/น้ำหนักเมื่อได้รับการยืนยัน ไฟล์เกณฑ์มีคะแนนรวม 100 คะแนน แต่ยังไม่มีข้อสรุปว่าจะเฉลี่ยคะแนนรวม หรือเฉลี่ยรายเกณฑ์ก่อนรวม และยังไม่ระบุน้ำหนักผู้ประเมิน

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | สูตร | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — เฉลี่ยคะแนนรวมรายผู้ประเมิน | `(Total E1 + Total E2 [+ Total E3]) / จำนวนผู้ประเมิน` | เข้าใจง่ายและตรวจสอบง่าย | รายงานรายละเอียดรายเกณฑ์ไม่ชัดเท่าตัวเลือก B |
| B — เฉลี่ยรายเกณฑ์แล้วรวม | หาค่าเฉลี่ยของแต่ละเกณฑ์จากผู้ประเมิน แล้วรวมตามน้ำหนักเกณฑ์ | โปร่งใส วิเคราะห์ความเห็นต่างรายเกณฑ์ได้ และรองรับน้ำหนักในอนาคต | ต้องกำหนดลำดับการปัดเศษให้ชัดเจน |
| C — กำหนดน้ำหนักผู้ประเมินไม่เท่ากัน | เช่น ประธาน 50% และผู้ประเมินอื่นแบ่งส่วนที่เหลือ | รองรับบทบาทพิเศษ | อาจไม่เป็นธรรมและไม่มีหลักฐานใน Proposal ว่าต้องใช้ |

> เมื่อผู้ประเมินทุกคนใช้เกณฑ์และน้ำหนักเดียวกัน และไม่มีการปัดเศษระหว่างทาง ตัวเลือก A และ B จะให้ผลทางคณิตศาสตร์เท่ากัน แต่ตัวเลือก B อธิบายผลและตรวจสอบรายเกณฑ์ได้ดีกว่า

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก B** และให้ผู้ประเมินทุกคนมีน้ำหนักเท่ากัน

สูตรแนะนำ:

```text
CriterionAverage(c) = SUM(SubmittedScore ของเกณฑ์ c) / SubmittedEvaluatorCount
FinalScore = SUM(CriterionAverage(c) × CriterionWeight(c))
```

กรณีคะแนนในแบบฟอร์มเป็นคะแนนหลังคูณน้ำหนักอยู่แล้ว ให้ `CriterionWeight = 1` และรวมค่าเฉลี่ยรายเกณฑ์โดยตรง

**ข้อความ Final Decision ที่แนะนำ**

> คะแนนสรุปคำนวณโดยเฉลี่ยคะแนน Submitted รายเกณฑ์จากผู้ประเมินที่ไม่ซ้ำกัน 2–3 คน แล้วรวมตามน้ำหนักเกณฑ์ ผู้ประเมินทุกคนมีน้ำหนักเท่ากัน

## RD-011 — การปัดเศษ

**[ข้อมูลจากไฟล์]** Proposal ระบุว่าต้องคำนวณตามหลักการปัดเศษที่งานทุนยืนยัน แต่ยังไม่กำหนดจำนวนตำแหน่งและจุดที่ปัด

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — ปัดเฉพาะคะแนนสุดท้าย 2 ตำแหน่ง | เก็บค่าระหว่างคำนวณเต็มความละเอียด และปัดตอนแสดง/ส่งออก Final Score | ลดความคลาดเคลื่อนสะสมและเหมาะกับการจัดอันดับ | ผู้ใช้ต้องเข้าใจว่าค่าที่แสดงระหว่างทางอาจถูกจัดรูปแบบเท่านั้น |

### [คำแนะนำหลักจาก AI]

**ข้อความ Final Decision ที่แนะนำ**

> ระบบเก็บค่าคำนวณเต็มความละเอียดและปัดเฉพาะ Final Score เป็นทศนิยม 2 ตำแหน่งด้วยวิธี ROUND_HALF_UP โดยไม่ปัดรายเกณฑ์ระหว่างการคำนวณ

## RD-013 — คะแนนที่กรอกได้ในหัวข้อดุลพินิจ

**[ข้อมูลจากไฟล์]** เกณฑ์ดุลพินิจระบุช่วง 0–10 และไฟล์เดิมพบคะแนนอื่นนอกเหนือจาก 0, 5 และ 10 จึงยังไม่ชัดว่าต้องเป็นตัวเลือกตายตัวหรือเลขอิสระ

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — เลขจำนวนเต็ม 0–10 | กรอกหรือเลือกจำนวนเต็มทุกค่า | ยืดหยุ่นและ Validation ชัด | ผู้ประเมินแต่ละคนอาจตีความระดับคะแนนไม่เหมือนกัน |
| B — เฉพาะ 0, 5, 10 | ใช้ระดับต่ำ/กลาง/สูง | สม่ำเสมอและใช้งานเร็ว | ความละเอียดต่ำและไม่สอดคล้องกับข้อมูลเดิมที่มีค่าอื่น |
| C — เพิ่มทีละ 0.5 ตั้งแต่ 0–10 | รองรับคะแนนละเอียด | ยืดหยุ่นสูง | อาจละเอียดเกินความจำเป็นและลดความสม่ำเสมอ |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก A** คือจำนวนเต็ม 0–10 และเพิ่มคำอธิบายระดับคะแนน เช่น 0–2, 3–4, 5–6, 7–8, 9–10 เพื่อช่วยให้ผู้ประเมินใช้เกณฑ์สอดคล้องกัน

**ข้อความ Final Decision ที่แนะนำ**

> หัวข้อดุลพินิจอนุญาตคะแนนจำนวนเต็มตั้งแต่ 0 ถึง 10 และต้องมีคำอธิบายแนวทางให้คะแนนแต่ละช่วง

### [ข้อเสนอแนะจาก AI] ตัวเลือก

## RD-017 — ข้อมูลหลายแถวต่อผู้สมัคร

**[ข้อมูลจากไฟล์]** ใน `Data_import_to_web(1).xlsx` พบแถวผู้สมัครหลักหนึ่งแถว และแถวถัดมาที่ช่องข้อมูลผู้สมัครว่าง แต่มีค่าเฉพาะคอลัมน์ กยศ. และทุน เช่น ประวัติหลายปี จึงมีลักษณะเป็น Continuation Row ของผู้สมัครคนก่อนหน้า

## RD-018 — ข้อมูลซ้ำตอน Import

**[ข้อมูลจากไฟล์]** Proposal กำหนดให้ระบบตรวจพบข้อมูลซ้ำ แสดงเลขแถวและรายละเอียดปัญหาก่อนยืนยัน Import แต่ไม่ได้กำหนดว่าจะ Reject, Skip หรือ Update

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — Reject ทั้งไฟล์ | พบ Error หรือ Duplicate หนึ่งรายการให้ยกเลิกทั้ง Batch | Transaction ชัดและไม่เกิดข้อมูลบางส่วน | ผู้ใช้ต้องแก้ไฟล์ทั้งหมดแม้มีปัญหาเพียงไม่กี่แถว |
| B — Import เฉพาะแถวที่ผ่าน | Skip แถวซ้ำ/ผิด และนำเข้าแถวที่ถูกต้อง | ใช้งานสะดวกและไม่เสียงานทั้งหมด | ต้องสื่อสารผล Partial Import ให้ชัดเจน |
| C — Upsert | หากพบรายการเดิมให้อัปเดตข้อมูล | ลดข้อมูลซ้ำและแก้ข้อมูลเดิมได้ | เสี่ยงเขียนทับข้อมูลที่เริ่มประเมินแล้ว |

### [คำแนะนำหลักจาก AI]

ใช้กฎแบบผสมดังนี้

1. Duplicate ภายในไฟล์เดียวกัน: ทำเป็น Error และไม่นำเข้าแถวที่ซ้ำทั้งหมดจนกว่าผู้ใช้แก้ไข
2. Duplicate กับข้อมูลในรอบทุน: ค่าเริ่มต้นเป็น `Skip/Error`
3. อนุญาต `Update` เฉพาะผู้ดูแลเลือกอย่างชัดเจน และเฉพาะผู้สมัครที่ยังไม่มี Evaluation
4. หากมี Evaluation แล้ว ห้ามแก้ข้อมูลสำคัญด้วย Import; ให้แก้ผ่านหน้าจอที่มี Audit หรือสร้างรอบนำเข้าแก้ไขโดยเฉพาะ
5. ระบบต้องสรุป `Inserted / Updated / Skipped / Failed` ก่อนยืนยัน

**ข้อความ Final Decision ที่แนะนำ**

> ระบบไม่ Upsert โดยอัตโนมัติ ข้อมูลซ้ำภายในไฟล์เป็น Error ส่วนข้อมูลซ้ำกับรอบทุนให้ Skip เป็นค่าเริ่มต้น และอนุญาต Update เฉพาะเมื่อผู้ดูแลเลือกและผู้สมัครยังไม่มี Evaluation

## RD-019 — ข้อมูลบังคับ

**[ข้อมูลจากไฟล์]** Proposal ระบุให้ตรวจสอบข้อมูลที่จำเป็นต่อการประเมิน แต่ไม่ได้กำหนดรายการ Required Fields อย่างเป็นทางการ ไฟล์นำเข้ามีข้อมูลจำนวนมากทั้งข้อมูลระบุตัวตน การศึกษา ค่าใช้จ่าย ครอบครัว ประวัติทุน และพิกัด

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — Required ขั้นต่ำ | บังคับเฉพาะข้อมูลระบุตัวผู้สมัครและแสดงรายชื่อ | Import ผ่านง่าย | อาจไม่มีข้อมูลเพียงพอสำหรับการประเมิน |
| B — Required ทุกคอลัมน์ | ทุกช่องต้องมีค่า | ข้อมูลครบ | ไม่เหมาะกับข้อมูลที่ไม่มีจริงหรือไม่เกี่ยวข้องกับผู้สมัครบางคน |
| C — Required แบบแบ่งระดับ | แยก Hard Required, Required for Evaluation และ Optional | สมดุลและอธิบาย Error ได้ดี | ต้องกำหนด Metadata ของแต่ละฟิลด์ |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก C**

| ระดับ | ฟิลด์ที่แนะนำ |
|---|---|
| Hard Required สำหรับสร้างผู้สมัคร | รหัสนักศึกษา, ชื่อ, นามสกุล, คณะ, สาขา, ชั้นปี |
| Required ก่อนเปิดให้ประเมิน | GPA และข้อมูลที่เกณฑ์ของรอบทุนอ้างอิงโดยตรง |
| Optional/Nullable | คำนำหน้า, โทรศัพท์, อีเมล, พิกัด, รายได้เสริม, รายละเอียดบิดา/มารดา, ผู้ให้อุปการะ, ประวัติ กยศ./ทุน หากไม่มีข้อมูล |
| System-supplied | รอบทุน, ผู้นำเข้า, วันเวลานำเข้า ไม่จำเป็นต้องอยู่ในทุกแถว |

ควรแยกคำว่า “ไม่มีข้อมูล” ออกจากค่า `0` เพราะรายได้ `0` มีความหมายต่างจากไม่ทราบรายได้

**ข้อความ Final Decision ที่แนะนำ**

> ใช้ Required Fields แบบแบ่งระดับ โดยรหัสนักศึกษา ชื่อ นามสกุล คณะ สาขา และชั้นปีเป็น Hard Required ส่วนฟิลด์ที่ใช้ในเกณฑ์ของรอบทุนต้องครบก่อนเปิดให้ประเมิน ฟิลด์อื่นอนุญาตให้ว่างตาม Data Dictionary

## RD-020 — รูปแบบวันที่และตัวเลข

**[ข้อมูลจากไฟล์]** ไฟล์ตัวอย่างมีวันที่ในรูปแบบข้อความภาษาไทย เช่น `09 ก.ค. 2569 13:36` และมีเครื่องหมาย `-` ในข้อมูลประวัติ ขณะที่ Proposal กำหนดให้ตรวจสอบข้อมูลผิดรูปแบบ แต่ยังไม่มีกฎมาตรฐาน

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — Template มาตรฐานเดียว | วันที่ `YYYY-MM-DD` หรือ `YYYY-MM-DD HH:mm`, ตัวเลขเป็น Numeric | ไม่กำกวมและทดสอบง่าย | ผู้ใช้อาจต้องแปลงไฟล์เดิม |
| B — รับรูปแบบไทยเดิม | รองรับเดือนภาษาไทยและปี พ.ศ. | สะดวกกับไฟล์ปัจจุบัน | Parser ซับซ้อนและเสี่ยงรูปแบบหลากหลาย |
| C — Flexible Parser พร้อม Preview | รับ ISO, `DD/MM/YYYY`, Excel Serial และ พ.ศ./ค.ศ. ที่กำหนดไว้ | รองรับไฟล์หลายแหล่ง | ต้องมี Warning และป้องกันวันที่กำกวม |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก C** สำหรับ Import และใช้ **ตัวเลือก A** เป็น Template ทางการ

กฎแนะนำ:

- จัดเก็บวันที่ภายในเป็น ISO/Database DateTime
- Template ใหม่ใช้ `YYYY-MM-DD` และ `YYYY-MM-DD HH:mm`
- รองรับ Excel Serial, `DD/MM/YYYY`, ปี พ.ศ. และเดือนภาษาไทยเฉพาะรูปแบบที่ประกาศไว้
- หากปีมากกว่า 2400 ให้แปลง พ.ศ. เป็น ค.ศ. โดยลบ 543 และแสดงค่าหลังแปลงใน Preview
- ช่องว่างและ `-` ให้ตีความเป็น `NULL` ไม่ใช่ 0
- ตัวเลขที่มี comma ให้ Normalize ก่อน Validation
- ฟิลด์จำนวนเงินเก็บเป็น `DECIMAL`; จำนวนคน/ชั้นปีเก็บเป็น Integer
- ค่าที่แปลงไม่ได้ต้องเป็น Error และห้ามเดา

**ข้อความ Final Decision ที่แนะนำ**

> Template ใหม่ใช้วันที่รูปแบบ ISO ส่วน Importer รองรับรูปแบบที่กำหนดไว้รวมถึง Excel Serial และปี พ.ศ. โดยต้องแสดงค่าที่แปลงแล้วใน Preview ช่องว่างหรือ `-` ให้เป็น NULL และค่าที่ตีความไม่ได้เป็น Error

## RD-021 — รูปแบบรายงาน

**[ข้อมูลจากไฟล์]** Proposal ระบุว่ารายงานต้องมีข้อมูลผู้สมัคร รายชื่อผู้ประเมินที่ Submit คะแนนรายเกณฑ์และคะแนนรวมรายคน จำนวนผู้ประเมิน จำนวนผล Submitted สถานะ ความคิดเห็น และคะแนนสรุป รวมทั้งต้องตรงกับ Result Summary และฐานข้อมูล แต่ยังไม่ได้กำหนดโครงสร้างแถว คอลัมน์ และลำดับ

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — หนึ่งผู้สมัครต่อหนึ่งแถว | Flatten ผู้ประเมินสูงสุด 3 คนเป็นชุดคอลัมน์ E1/E2/E3 | เหมาะกับการพิจารณาและจัดอันดับ | จำนวนคอลัมน์มาก โดยเฉพาะคะแนนรายเกณฑ์ |
| B — หนึ่งผู้ประเมินต่อหนึ่งแถว | ผู้สมัครหนึ่งคนมี 2–3 แถว | วิเคราะห์รายผู้ประเมินง่าย | คะแนนสรุปและข้อมูลผู้สมัครซ้ำหลายแถว |
| C — Excel หลาย Sheet | `Summary`, `Evaluator Detail`, `Criterion Scores`, `Comments` | ครบถ้วน อ่านง่าย และใช้วิเคราะห์ต่อได้ | CSV ไม่รองรับหลาย Sheet ต้องแยกเป็นหลายไฟล์ |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก C** สำหรับ Excel และส่งออก CSV อย่างน้อย 2 ไฟล์ ได้แก่ `applicant_summary.csv` และ `evaluation_detail.csv`

โครงสร้างแนะนำ:

1. **Summary — หนึ่งผู้สมัครต่อหนึ่งแถว**
   - รอบทุน, รหัสนักศึกษา, ชื่อ-นามสกุล, คณะ, สาขา, ชั้นปี, GPA
   - Submitted Count, Active Evaluation Count, Applicant Status
   - Evaluator 1–3, Total ของแต่ละคน, Final Score
   - Finalized At หรือหมายเหตุ `Closed Incomplete`
2. **Evaluator Detail — หนึ่ง Evaluation ต่อหนึ่งแถว**
   - ผู้สมัคร, ผู้ประเมิน, สถานะ, Submitted At, คะแนนรายเกณฑ์, Total, Comment
3. **เรียงลำดับค่าเริ่มต้น**
   - ผู้สมัครที่มี Final Score: คะแนนมากไปน้อย
   - คะแนนเท่ากัน: รหัสนักศึกษาจากน้อยไปมาก
   - `Closed Incomplete` อยู่ท้ายรายงาน
4. ความคิดเห็นยาวควรอยู่ใน Detail หรือ Comments Sheet ไม่ควรอัดไว้ใน Summary

**ข้อความ Final Decision ที่แนะนำ**

> รายงาน Excel ใช้หลาย Sheet โดย Summary เป็นหนึ่งผู้สมัครต่อหนึ่งแถว และ Evaluation Detail เป็นหนึ่งผู้ประเมินต่อหนึ่งแถว ส่วน CSV ส่งออก Summary และ Detail แยกไฟล์ เรียง Final Score จากมากไปน้อยและรหัสนักศึกษาจากน้อยไปมากเมื่อคะแนนเท่ากัน

## RD-022 — ข้อมูลส่วนบุคคลในรายงาน

**[ข้อมูลจากไฟล์]** Proposal ระบุว่าข้อมูลผู้สมัครมีข้อมูลส่วนบุคคลและข้อมูลอ่อนไหว ต้องจำกัดสิทธิ์ตามบทบาท ผู้ดูแลระบบเป็นผู้ส่งออกรายงาน และระบบต้องบันทึกผู้ส่งออกกับเวลา แต่ยังไม่ได้กำหนดคอลัมน์อ่อนไหวที่อนุญาต

### [ข้อเสนอแนะจาก AI] ตัวเลือก

| ตัวเลือก | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A — Minimal Report | ส่งออกเฉพาะข้อมูลที่จำเป็นต่อการตัดสินผล | ลดความเสี่ยงข้อมูลรั่วไหล | ผู้ดูแลอาจต้องเปิดระบบเพื่อดูข้อมูลเพิ่มเติม |
| B — Full Admin Report | รวมข้อมูลติดต่อ รายได้ และครอบครัวทั้งหมด | ใช้งานต่อได้ครบในไฟล์เดียว | ความเสี่ยง PDPA สูงและไฟล์ควบคุมยากหลัง Export |
| C — แยก Template ตามวัตถุประสงค์ | Committee Summary, Operational Contact และ Restricted Detail | ใช้หลัก Least Privilege และตอบโจทย์หลายงาน | ต้องจัดการสิทธิ์และ Template หลายแบบ |

### [คำแนะนำหลักจาก AI]

เลือก **ตัวเลือก C**

| Template | ข้อมูลที่ควรมี | สิทธิ์ |
|---|---|---|
| Committee Summary | รหัสนักศึกษา ชื่อ สาขา ชั้นปี GPA คะแนน สถานะ และข้อมูลประกอบที่จำเป็นต่อการพิจารณา | ผู้ดูแล/คณะกรรมการที่ได้รับอนุญาต |
| Operational Contact | ชื่อ เบอร์โทร อีเมล และสถานะ | ผู้ดูแลที่ต้องติดต่อผู้สมัคร |
| Restricted Detail | รายได้ครอบครัว ข้อมูลบิดา/มารดา ผู้ให้อุปการะ และข้อมูลละเอียดอ่อน | ผู้ดูแลระดับจำกัด พร้อมเหตุผลการ Export |

กฎเพิ่มเติมที่แนะนำ:

- ไม่ส่งออกเลขบัตรประชาชนโดยค่าเริ่มต้น
- หากจำเป็นต้องส่งออก ให้ Mask หรือแสดงเฉพาะ 4 หลักท้าย และต้องมีสิทธิ์พิเศษ
- ผู้ประเมินทั่วไปไม่ควรมีสิทธิ์ Export รายงานรวม
- บันทึก Export Audit: ผู้ใช้ เวลา รอบทุน Template จำนวนรายการ และเหตุผลสำหรับ Restricted Export
- ไฟล์ Export ควรมีชื่อไฟล์ระบุรอบและเวลา และอาจมีข้อความชั้นความลับ

**ข้อความ Final Decision ที่แนะนำ**

> จำกัดการส่งออกรายงานรวมไว้ที่ผู้ดูแลระบบ และแยก Template ตามวัตถุประสงค์ ใช้ข้อมูลเท่าที่จำเป็น ไม่ส่งออกเลขบัตรประชาชนโดยค่าเริ่มต้น และบันทึก Audit Log ทุกครั้งที่ Export

# 4. รายการคำถามสั้นสำหรับใช้ในประชุมยืนยัน

ให้ผู้มีอำนาจตอบโดยเลือกตัวเลือกหรือแก้ข้อความที่แนะนำ

| ID | คำถามที่ต้องตอบ |
|---|---|
| RD-008 | อนุมัติ Controlled Reopen ก่อนปิดรอบ โดยหัวหน้างานทุนและเก็บ Revision เดิมหรือไม่ |
| RD-009 | อนุญาตให้ผู้ประเมินยกเลิก Draft ของตนเองและคืนช่องทันทีหรือไม่ |
| RD-010 | ยืนยันสูตรเฉลี่ยรายเกณฑ์ โดยผู้ประเมินทุกคนมีน้ำหนักเท่ากันหรือไม่ |
| RD-011 | ยืนยันปัดเฉพาะ Final Score เป็นทศนิยม 2 ตำแหน่งหรือไม่ |
| RD-012 | ยืนยัน 10 เกณฑ์รวม 100 คะแนนเป็น Template เริ่มต้นและใช้ Criteria Versioning หรือไม่ |
| RD-013 | คะแนนดุลพินิจเป็นจำนวนเต็ม 0–10 หรือจำกัดเฉพาะ 0, 5, 10 |
| RD-014 | อนุมัติชื่อใหม่ของเกณฑ์ “ค่าใช้จ่ายประจำวัน” สองรายการหรือไม่ |
| RD-015 | ยืนยัน Business Unique Key เป็น `รอบทุน + รหัสนักศึกษา` หรือไม่ |
| RD-017 | อนุมัติ Template แบบหลาย Sheet และระยะเวลาที่จะเลิกรองรับ Continuation Row เมื่อใด |
| RD-018 | อนุญาต Update ข้อมูลเดิมผ่าน Import ก่อนเริ่มประเมินหรือให้ Skip ทุกกรณี |
| RD-019 | ฟิลด์ใดต้องครบก่อน Import และฟิลด์ใดต้องครบก่อนเปิดให้ประเมิน |
| RD-020 | รูปแบบวันที่ใดบ้างที่ต้องรองรับนอกจาก ISO |
| RD-021 | อนุมัติรายงานแบบหลาย Sheet และลำดับคอลัมน์ที่เสนอหรือไม่ |
| RD-022 | ใครบ้างมีสิทธิ์ใช้ Committee, Contact และ Restricted Export Template |

# 5. เกณฑ์ปิด Requirement Baseline

ก่อนเปลี่ยนสถานะเอกสารเป็น `Current` ควรดำเนินการดังนี้

1. ผู้ยืนยันหลักเลือกหรือแก้ไขคำตอบของ RD-008 ถึง RD-022
2. บันทึกชื่อผู้อนุมัติ วันที่ และเหตุผลของการเลือกแต่ละข้อ
3. แนบ Template เกณฑ์, Import Template และ Report Template ฉบับที่อนุมัติ
4. กำหนด Test Case จาก Final Decision โดยเฉพาะ Reopen, Calculation, Rounding, Duplicate Import และ PII Export
5. เปลี่ยนสถานะ Critical/High ทั้งหมดไม่ให้เหลือ `Open Decision`
6. ลงนามหรือยืนยันทางอีเมลว่า `Requirement Baseline Approved`
